# Scout lanes

Use this catalog to see what each lane checks, when it runs, and whether it can ever block a pull request. The lane IDs, triggers and modes come from the registry in `internal/engine/lanes.go`. The intended scope of each lane is in REQ-17, REQ-62 and REQ-63. Where the design and the code differ, the code's current behaviour is noted below.

Modes: **blocking-eligible** lanes can block once a check is activated. **report** lanes record issues but never block. **signal** lanes record measurements only.

## Notes

- Blocking applies only under the `guardian` profile, only for checks listed under `blocking.checks` in the policy, and only to `introduced` or `regressed` findings. Until then, matches show up as `would_block`.
- `guardrails` and `delta` run on `scout diff` only, so a `scout assess` run lists them as `skipped` (`docs/STATUS.md` §1).
- An opt-in lane that cannot run reports `skipped (not opted in)` or `skipped (no model CLI)` and does not change the exit code. If a required lane does not finish, the exit code is `2`.
- A value that could not be measured is `unmeasured` with a reason, never 0. For example, CRAP without a coverage artifact for the same revision, or `pr_effort` without PR metadata.
- The `rubric` lane (REQ-67) is planned for Phase 5 and is not in the registry.
- `scout readiness --matrix` prints which capabilities are available for each language in the target repository.
- `association` always has a health row, including when disabled. Its summary status is `ran (n)` (attempted clusters, not HTTP requests), `failed` when every attempted call fails, or `skipped (<reason>)`. Partial call success still reports `ran (n)`; individual failures remain in association records. It never changes gate exit codes.
- Association uses the explicit `assess --from/--to` range or GitHub push event `before`/`after`; without a range it reports `skipped (push range unavailable)` rather than guessing a prior commit. PR/fork and non-default-branch GitHub pushes never call Jev.
- Association fingerprints include frozen question text, thresholds, Jev model, Terra prompt digest and fallback model, not catalogue content. Changed fingerprints mark prior decisions stale without removing their labels or automatically redeciding them. Every decision discloses provisional thresholds.
- `association-fallback` is optional and never changes gate exit codes. Without its own consent it is `skipped (no consent)`; without codex it is `skipped (no model CLI)` regardless of the configured model-CLI provider. Jev continues. It never escalates earlier-run rows, Jev failures, Jev caps or per-merge caps. Answers update ownership before the next merge. One retry precedes `terra_failure`; attempt and pending caps leave excess clusters unresolved as `fallback_cap` and `pending_cap`. Health is `failed` only when every attempted cluster fails; partial success is `ran (n)`.
