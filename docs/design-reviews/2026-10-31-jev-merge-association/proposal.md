# Proposal (DRAFT, pending innovation council sign-off): merge-time area association

Draft revision 2.8 of `docs/scout-design.md` (CLAUDE.md design rule 1: not adopted until the council signs off with zero issues; review rounds go in this directory as `round-<N>.md`; round 1 found 14 issues and round 2 found 10, applied here and in the design). Sources: R-055, R-056, R-057, R-058, R-059, R-060, R-061 (`docs/research-ledger.md`); `evaluation/x2d-postrun-tuning/README.md`, `FROZEN-8-10.md`, `axum/README.md`.

## Problem

After onboarding the agent map runs only on a manual `scout map --refresh` (Appendix 21). Files that merges add or move in between have no agent-derived area. Today they are listed as unowned and get a directory scope (§4 Unowned files); `internal/areas` only folds a whole agent map into areas (`Reconcile`, file-set Jaccard ≥ 0.5) and has nothing for single merges. A folder guess is the only cheap alternative, and it is poor: on 92 unseen fastapi window clusters (rounds 8–10) the directory baseline B2 assigned correctly 0.766 of the time with recall 0.636 (unresolved counted as a miss); on the 200 clusters of rounds 1–7 it was 0.452 / 0.380 (71/187; 0.420 on resolved clusters).

## Proposed flow (default-branch push runs only; never PR runs)

1. For each first-parent merge in the push, take the files it added, moved or modified, and apply the measured residual rules (`evaluation/x2d-postrun-tuning/axum/pilot/frontend.py` `owned_classify`, the front end of both runs, `build_units.py:247`; `classify` is only the catalogue-free pre-pass proxy). An active area, or an association record that assigns the file to an active area, counts as an owner, and a pending area takes the role of the measured pool: deleted files are dropped, and so are markdown and media files (`excluded_reason`); a modified file that an owner holds is not decided, and a modified file that no owner holds and no heuristic feature owns is counted as a coverage gap and is not decided; a renamed file inherits its old path's owner, or stays in its pending area, unless it is empty; an added file with an owned variant sibling (same normalised directory, variant stem and extension) inherits that owner; a file owned only by a heuristic feature is decided whether added, moved or modified (rule (f)); every other added or moved file is residual, and clusters made only of empty files are inert. A file that inherits an owner by the rename or variant-sibling rule gets an association record with outcome `inherited` (rule `rename` or `variant`, the old path or sibling, the inherited area ids, never a pending area; no model call), with the Jev and fallback fields empty. Its label comes from that record, and it counts as an owner afterwards. A renamed file whose old path is in a pending area and held by no owner gets no association record, is not an owner and is not decided, even when a heuristic feature owns it, as in the measured runs a pooled file owned nothing and a pooled rename was resolved before rule (f) (`frontend.py` `owned_classify` `renamed_pooled`, `is_pooled`, `variant_owners`); it replaces its old path in that pending area's file set. When an owner holds the old path, the renamed file inherits that owner as above and the old path leaves the pending area's file set (`gold.py`: an owned rename moves to its owners, never to the pool). Inherited records are not decided clusters, enter neither guard rate, and are not counted by `max_per_run` or the per-merge cluster cap. The measured cross-scope rename rule (`frontend.py` `scope`, repository-specific prefixes) and the measured translation rule (`excluded_reason`: any `docs/<2–3-letter directory>/` other than `docs/en/`, a fastapi layout that also matches `docs/api/` or `docs/src/`) have no Scout equivalent and are not applied; these are unmeasured differences. Group the remaining files by normalised parent directory and variant stem (`frontend.py` `clusters`), so one merge can produce several clusters (fastapi: 92 clusters in 41 PRs). At most 10 clusters per merge are decided, hash-sampled as measured; the rest are `unresolved (pr_cap)`. Jev and the fallback get the measured state: unit paths, change kind, role, and the first 60 lines of each member; PR title, body and changed paths from `--fetch-pr-metadata` (Appendix 17; absent metadata is recorded `pr_metadata: absent`, an unmeasured condition); the diff summary; every active area with id, title, summary and at most 5 sample files. `merge.which_area` is asked in a second permutation for the measured 20 % hash-selected subset only. With fewer than 2 or more than 255 active areas (the Choice limit), `association` reports `skipped (catalogue size)`.
2. For each cluster, Jev (pinned model, v1 questions) reads `merge.covered` ("does any listed area cover this change?") and then `merge.which_area` (a permuted choice over the whole catalogue). Policy thresholds: `which_area` confidence ≥ **0.535** assigns; `covered` answers `none` iff P(true) ≤ **0.40** (covered score threshold s = **0.60**). Permutation disagreement or a score below threshold is `unresolved`.
3. Every cluster Jev leaves `unresolved` or calls `none` goes to the reasoning-model lane: `codex exec -m gpt-6.1-terra -c model_reasoning_effort=high`, read-only sandbox, ephemeral, scrubbed environment, no tools. Prompt `terra_prompt_v1.txt` (sha256 `ca24fd76…5e76`), input = cluster, PR title/body, diff summary and the full catalogue. It answers `existing` (an area id) or `new` (title, summary, reason).
4. `existing` assigns the cluster to that area as an association record (cluster id, files, area id, decision); the files are not written into the area's `FileSet`, so `Reconcile` and its Jaccard read agent-map file sets only. `new` records a **pending area** (title, summary, file set, reason; Appendix 23): an `areas` record with `status: pending` and its provenance, exported in `areas.jsonl`, `Active()` false so no deterministic lookup treats its files as owned, a label only that never re-keys an issue or a signal series (areas are labels, §4). It is recorded on a fallback `new` answer and never accepted by a model. Pending areas are not offered to Jev or the fallback (the measured setting), so one new concern can produce several pending areas; the summary lists them with their files. `Reconcile` neither matches nor retires a pending area. After a completed agent map, a pending area whose files that exist at the mapped revision are all in active areas' `FileSet`s is marked `superseded` and listed, never accepted or deleted automatically, and an association record whose files that exist at the mapped revision are all in active areas' `FileSet`s is superseded by the map; heuristic-feature ownership supersedes neither, because rule (f) decides such files. Only a maintainer's accept, or merge into an existing area, changes a pending area's status (§6); an accepted area becomes active with origin `association` and records the maintainer's acceptance (`accepted_by`, `accepted_at`) in the `areas` payload. From then on `Reconcile` matches it like any area, updating file set, title, Clawpatch ids and origin. It never retires an area that carries a maintainer acceptance, before or after a match; an unmatched one is kept.
5. Nothing is left unowned silently. After one retry, a Terra error, a timeout, a session that ran any command, a CLI-reported model or effort other than `gpt-6.1-terra` / `high`, an unparsable answer or an unknown area id leaves the cluster `unresolved (terra_failure)`; a Jev failure, model mismatch or `policy.decisions` cap leaves it `unresolved (jev_failure)` or `unresolved (jev_cap)` and it is not escalated; clusters beyond `fallback.max_per_run` are `unresolved (fallback_cap)`. All are counted and listed in the summary and `readiness`, never a folder guess.
6. Every association decision (Jev-only or with fallback) is a row of a new `associations` table, one per decided cluster per run, plus one per inherited file: run id, decision time, the `LastAgentRefreshAt` in force when decided (null before onboarding), merge commit, cluster key and files, Jev scores and composed outcome, escalation reason, CLI name and version, reported model and effort, prompt digest, inputs digest, catalogue digest, raw answer, retries, latency, outcome, whether `association-fallback` was skipped in that run and why, and `stale`. It is exported as `state/v1/associations.jsonl` (added to the §7.2 export list), so the log, the guard window and `catalogue-stale` survive between runs on hosted runners; an export with no `associations.jsonl` (every export before revision 2.8) imports as no association records and the manifest lists the file as `absent`. The guard window uses only rows whose recorded `LastAgentRefreshAt` equals the current one, in decision-time order; the flag is set by the first window in that generation that exceeds a limit and holds until `LastAgentRefreshAt` changes; commit timestamps are never used. The store schema becomes `user_version` 13 (§3.3); under Appendix 22(a), whose schema number becomes 13 (Appendix 23(e)) and whose refusal rule is unchanged, a store at 12 is refused with the existing re-baseline message. Jev request bodies stay redacted as §6 requires.

## Policy keys and defaults (from FROZEN-8-10)

`mapping.association.enabled` (default **false**, opt-in; `association` needs `decision-egress`; `association-fallback` separately needs its own model-CLI consent), `.t_choice` 0.535, `.covered_score` 0.60, `.fallback.model` `gpt-6.1-terra` and `.fallback.effort` `high` (pinned; `codex exec` only, no provider key), `.fallback.timeout` 900 s, `.fallback.max_per_run` 40 (an **[ASSUMPTION]** cost ceiling: fastapi averaged about 2.2 clusters per merged PR that left residual files (92 in 41 such PRs; most merges leave none: axum 120 clusters from 69 of 905 first-parent commits) and about 27 of 100 escalate) and `.max_pending_per_run` 10 **[ASSUMPTION, not measured]**, and the refresh-guard keys below. A model mismatch reported by the CLI voids the answer. Each association record stores the catalogue digest it was decided against; a catalogue change alone does not make it stale. A change to a threshold, the question text, the prompt digest, the Jev pin or the fallback model marks prior records `stale`; a stale record keeps its label, is shown `stale` and is never re-decided automatically. The association thresholds are policy values of this provisional lane, not tuned operating points keyed to a question version. Enabling the lane is the maintainer's acceptance of `provisional` under §6, so a `merge.which_area` version change caused only by the catalogue (its options) neither makes them stale nor stops the lane. Every association record is disclosed `thresholds provisional`.

## Lane placement

Two optional push-only `signal` lanes, because §3.4 allows one `requires` per lane: `association` (`requires: decision-egress`, Jev) and `association-fallback` (`requires: model-cli`; runs only on clusters `association` produced in the same run). With `enabled` false, no Jev key, `decision-egress` not acknowledged, or egress not allowed for the trigger, both lanes report `skipped (reason)`, no model is called, and residual files keep their directory scope as in revision 2.7. If `association` ran but there is no `codex` on `PATH` (the normal case on GitHub-hosted runners, R13) or the fallback consent is absent, `association-fallback` reports `skipped (no model CLI)` or `skipped (no consent)` and the clusters Jev left `unresolved` or `none` stay unowned, counted and listed. Health follows §6 Lane health and never changes the exit code. Fork and PR runs: not run. The fallback looks for `codex` only and never runs `claude`; like the agent map it is an exception to Appendix 22(c). Consent: `association` needs `decision-egress`; `association-fallback` captures its own model-CLI consent at `scout init` (§6) naming `codex` / OpenAI and the content sent (file excerpts, PR title and body, catalogue); `authorize-egress` does not apply because Clawpatch is not invoked. Cluster text is redacted by the existing sanitizer (not an injection defence; the prompt treats it as data and the output is only a label).

## Cost and latency (README, descriptive)

Jev ≈ $0.0013 per cluster in rounds 8–10 ($0.1178 / 92; $0.0014 over rounds 1–7). About 27 of 100 clusters escalate (25 of 92 in rounds 8–10; 54 of 200 in rounds 1–7). Terra latency per call: median 4.3 s, p90 4.9 s, max 5.9 s in rounds 8–10 (median 5.5 s in rounds 1–7). Terra's own cost is on the user's Codex subscription and was not measured in dollars. A push with 30 residual clusters would add about 8 calls, roughly 40 s sequential.

## Evidence and its limits

fastapi rounds 8–10 (R-057), 92 unseen clusters, one run, settings frozen and committed first (`c55a40d`): Jev+Terra P_assign 0.922 [0.840, 0.964] (71/77), recall 0.922, unresolved 0; new-area P / R 0.867 / 0.867 (13/15). Jev-only: P 0.955, recall 0.831, unresolved 0.109; B2 0.766 / 0.636. Terra was right on 20 of 25 escalations, 0 failed calls. Rounds 1–7 (where the prompt was iterated): P_assign 0.899, recall 0.856.

axum rounds 1–5 (R-058, corrected by R-060; `evaluation/x2d-postrun-tuning/axum/README.md`), 109 clusters, the same frozen settings, no tuning: Jev+Terra P_assign **0.622 [0.514, 0.719]** (51/82), resolved recall 0.810, unresolved 0; new-area P 0.852 (23/27), R 0.500 (23/46); Jev-only 0.610; B2 0.556 (interval overlaps). **The fastapi result did not replicate.** 23 of the 31 wrong assignments are gold-none clusters (a cluster no catalogue area describes, assigned to an existing area; of the 46 gold-none, 37 are `gap`, a responsibility that existed before the change, and 9 are `new`): 46 of 109 axum clusters (42 %) are gold-none against 15 of 92 (16 %) on fastapi, and Jev rarely answers `none` (Jev-only new-area recall 0.217, 10/46; the fallback raises it to 0.500, 23/46, but never sees clusters Jev assigns). Precision therefore depends on the gold-none share. Whether catalogue age caused it is **[INFERENCE]**, and the data weigh against age as the sole cause: round 1, 0–3 months after the catalogue, already has 13 of 23 gold-none, and the share does not rise with age (13/23, 5/20, 3/22, 15/24, 10/20). An incomplete onboarding catalogue (37 of 46 `gap`; 179 files unowned at C0) is an equally open explanation. Clusters run 0–3.4 years after the catalogue. Both runs teacher-forced membership: each round began from the previous round's gold, and gold `none` minted no area. The product feeds its own decisions forward, so error accumulation over merges and duplicate pending areas are unmeasured. Escalations 29 per 100, Terra median 5.6 s, Jev ≈ $0.0009 per cluster.

Limits: two repositories (Python, Rust); labels are agent-made (`agent_reviewed`); thresholds and prompt were developed on fastapi rounds 1–7; both test runs are development runs under no preregistration and no council review, so HD6 stays `inconclusive`. The user (R-059) accepts this evidence for a provisional opt-in lane only, as an exception to design rule 3; the lane is off by default and X11 is the signed-off test that upgrades or removes it. R-059 was taken before the axum result was reported; the user's confirmation after seeing it is recorded below (U1).

## Risks

- **Spurious or forced assignments.** axum: 23 of 31 wrong assignments were gold-none clusters assigned to existing areas (P_assign 0.622; 37 `gap` / 9 `new` among the 46 gold-none); fastapi rounds 6–7: 12 of 14 `none` answers were gold-covered clusters of one PR. Mitigation: opt-in, off by default; pending status, maintainer-only acceptance, log of the reason; refresh guard (below); no identity impact.
- **Near-duplicate areas (HD7).** Catalogue duplicates split Jev's choice; cross-scope duplicate checking is unvalidated (R-054).
- **Provider drift.** Jev, `gpt-6.1-terra` and the `codex` CLI change under pins; thresholds were tuned on one Jev version. Mitigation: pins, staleness disclosure, re-measure on version change.
- **Cost / latency** per push, bounded by the cap; the lane is optional.
- **Prompt overfit** to fastapi rounds 1–7; v2 of the prompt was worse, v1 kept.
- **Per-decision minimums:** `merge.which_area` was `tuned-provisional` (held-out below minimums); `merge.covered` is untunable at the skill's minimums (13 gold-none of 200). The thresholds here are chosen policy, not a tuned and validated operating point.

## Refresh guard (design only; defaults from fastapi, none tuned on axum)

Because precision depends on the gold-none share, Scout tracks over the last `N` = `window_merges` default-branch merges that produced residual clusters (evaluated once ≥ `min_clusters` clusters) the fallback rate (clusters Jev left `unresolved` or `none` ÷ residual clusters, whether or not the fallback ran) and the pending-new rate (valid `new` answers ÷ residual clusters, both counted over the window's merges decided in runs in which `association-fallback` was not skipped and in which the fallback answered every cluster Jev left `unresolved` or `none`; a merge decided in a run in which `association-fallback` was skipped, even one with no such cluster, or with a cluster left `unresolved (fallback_cap)` or `unresolved (terra_failure)`, is left out). The pending-new rate counts valid `new` answers before the pending cap. It is `unmeasured` while those merges hold fewer than `min_clusters` residual clusters (for example, on hosted runners without `codex`) or no cluster the fallback answered (for example, when every fallback call fails). Clusters `unresolved (jev_failure)`, `unresolved (jev_cap)` or `unresolved (pr_cap)` enter neither rate. Clusters `unresolved (fallback_cap)` or `unresolved (terra_failure)`, and clusters not sent because `association-fallback` was skipped (`no model CLI`, `no consent`), count in the fallback rate only. If the fallback rate exceeds 0.40 (1.5 × fastapi's ~27 per 100) or the pending-new rate exceeds 0.20 (1.25 × fastapi's ~16 % gold-none), the summary recommends a manual `scout map --refresh` and association output is flagged `catalogue-stale` (still assigned and logged) until a manual agent map completes. Keys `mapping.association.guard.{window_merges, min_clusters, fallback_rate_max, pending_new_rate_max}` = 20, 20, 0.40, 0.20, all **[ASSUMPTION]**. Honest limits: the limits were written after the axum figures were known. Compared at round granularity with the development data **[INFERENCE: no per-merge replay was run]**, the guard also fires on fastapi: rounds 8–9 (21 PRs, 44 clusters) give a fallback rate of 0.45 (20/44) and a pending-new rate of 0.32 (14/44), on the run that scored P_assign 0.922. Pooled escalation rates do not separate the repositories (29.4 against 27.2 per 100). Neither rate sees axum's main error: 30 of the 31 wrong assignments are Jev assignments, which are never escalated. Expect `catalogue-stale` flags on healthy catalogues; if the cause is an incomplete onboarding catalogue, a refresh with the same mapper may not restore precision. The guard's recall and false-fire rate are unknown; X11 tests them.
