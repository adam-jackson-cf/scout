### Decision 1 — state migration

1. **Schema history.** `internal/state/store.go:24` `const schemaVersion = 12`; `Store.migrate` (`store.go:231-337`) is a ladder `if current == N` from 0 to 12: v1 = `schemaV1` (`:338-352`), v2 = inline `inventory_snapshots` (`:249`), v3 = `schemaV3` (`:354-358`), v4 = `migrateV4` (`internal/state/progress.go:468`, `plan_jobs` + backfill + shell-payload rewrite of unfinished runs), v5 = `migrateV5` (`internal/state/issue_migration.go:25`, the v1 re-anchor), v6–v10 and v12 = `schemaV6` (`would_block.go:13`), `schemaV7` (`signals.go:17`), `schemaV8` (`annotations.go:19`), `schemaV9` (`ingested.go:13`), `schemaV10` (`prmeta.go:11`), `schemaV12` (`areas.go:16`); v11 changes JSON payloads only, no DDL (`store.go:315-320`).
2. **What released.** `git show <tag>:internal/state/store.go` gives `schemaVersion = 12` for **every** tag v0.1.0 to v0.1.5. At the initial import (`41ea1eb`, 2026-10-22, "Scout v1 Go implementation") it was 3; Phase 1 (`945ac4d`, 2026-10-23 09:08) made it 5, Phase 2 (`fccc137`, `4bab5c0`, `aac3ca7`) 6–8, `e86feb8` 11, `d00aac1` 12. So versions 4–11 existed only as development builds on 2026-10-23 before v0.1.0 (14:29): no release ever wrote a store below 12. Versions 1–3 are the Scout v1 implementation's.
3. **Where v1 stores live.** The v1 nightly workflow bundled the whole `.scout` directory, `state.sqlite` included, to S3 (`scripts/bundle-state.sh` at `41ea1eb`, `create --state-dir REPOSITORY/.scout --output OUTPUT.tar.gz`; `scout-nightly.yml` at `41ea1eb` lines 6–7 cron `23 3 * * *`, 43–81 AWS/S3). Both were removed at `fccc137` (state moved to the `scout/state` branch). So a `user_version` 3 store can exist in an S3 bucket or on a machine that ran the v1 nightly or the v1 binary; whether any outside the author's environment does is **unobserved** (no access to any bucket).
4. **The SQLite file is not the durable baseline.** Design §7.2: "SQLite stays the local transactional store"; "Never commit `.sqlite`/WAL"; the durable baseline is the `scout/state` export. In CI the store is created fresh in the checkout (`.scout/state.sqlite`, `store.go:68,86`) and rebuilt by `scout state restore` (`cmd/scout/state_cmds.go:127`, import into a fresh store, `internal/state/export.go:452`); `.github/workflows/scout-guardian-trusted.yml:149-160` restores before every trusted run. Neither workflow caches `.scout`.

No per-record version. The decode of records is lenient JSON (`decode`, `store.go`), so the format has not needed a bump. Observed in the wild: `git log origin/scout/state` shows 17 publishes from 2026-10-23 14:27Z to 2026-10-24 11:25Z, all manifests `schema: scout.state/v1`; the tip's `issues.jsonl` has 69 issues, 69 with `anchor`, 0 with `legacyId`. ### Decision 2 — legacy baseline "no lane health"

1. **The branch.** `resolveBase` (`internal/engine/diff.go:326`): `case imported.Gaps == nil:` banner `baseline carries no lane health; comparison recomputed` (`:341-342`), then the paired recompute (`pairedBaseScan`). `BaseState.Gaps` doc (`:27-29`): "nil means the baseline carries no lane health (a legacy export), which forces a recompute." `cmd/scout/diff.go:45-50`: `Gaps` is set only when `loaded.Uninspected != nil`. `internal/baseline/load.go:22-24` carries the same nil-means-legacy convention; `state.ManifestMeta.Uninspected` (`export.go:204-214`) is omitted from the manifest when nil (`:251-252`).
2. **Design text.** Base line 188 (§7.2): "an empty list means all were inspected, an absent field means a legacy export); otherwise the run takes the paired recompute with a banner naming the reason (… `baseline carries no lane health` …)". Test: `internal/engine/base_gaps_test.go:127` `TestImportedBaselineWithoutLaneHealthIsRecomputed`.
3. **When legacy manifests were written.** `git log -S'Uninspected' -- internal/state/export.go` → `480949a` (2026-10-23, "findings in lanes the base did not inspect are unknown"). `git show <tag>:internal/state/export.go | grep -c Uninspected`: v0.1.0 **0**, v0.1.1 **0**, v0.1.2–v0.1.5 **10**. So a manifest without `uninspected` comes from a publish by v0.1.0 or v0.1.1 (or a development build before `480949a`), or, in any release before this cutover, from a publish by a store with no finalized run and no imported lane health (Fact 2.5).
4. **What is in the wild.** The dogfood caller pinned v0.1.0 at `aac3ca7` (2026-10-23 11:32), v0.1.1 at `404f69b` (15:05 +0100), later v0.1.4, v0.1.5 (`git show <commit>:.github/workflows/scout-nightly.yml`). The `origin/scout/state` branch: all 17 manifests carry `uninspected` (checked per commit with `git show <commit>:state/v1/manifest.json`); the tip is `uninspected: []`. Other repositories' baselines were not observed.
5. **Where a missing field is read.** Only `LoadBase` (`internal/baseline/load.go:41-45`, differential runs) uses `Uninspected`. `Store.Import` (`export.go:452`) reads revision, digests and repository ID from the manifest (`:578`, `:615`) and, whenever revision or digests are set, stores the whole `ManifestMeta`, `Uninspected` included, under the `export_base` metadata key (`:618-621`); `Store.baseInfo` returns that value when the store has no finalized run (`:370-376`), so a publish before any finalized run re-emits the **imported** revision, digests and `uninspected`. `RenderManifest` omits a nil `Uninspected` (`:251-252`), so a publish from a store with no finalized run and no imported base also writes no field, in any release. `baseline.MergeState` (`merge.go:124-128`) reads the freshly exported local manifest and `wouldBlock` from the current one. So `state restore` does not read the field to accept a manifest, but what it imports decides what the next publish writes (Decision 2).
6. **Failure path.** A `LoadBase` error returns from `resolveBase` as `load baseline: …` and `Diff` ends `fail(err)` → `UnavailableReport` (`diff.go:82-88`, `:204-206`): exit 3 (`unavailable`, design §7.4), which the `report` profile shows as a neutral check (§7.3).

### Decision 3 — model-CLI provider order

1. **Two orders.** `modelcli.Detect("")` tries `claude` then `codex` (`internal/modelcli/modelcli.go:39-58`, `candidates := []Name{Claude, Codex}` at `:48`). `(*Client).resolveProvider` (`internal/clawpatch/provider.go:34-55`) tries `codex` then `claude` (`:46`), annotated "(Clawpatch's own default)".
2. **Callers of the `claude`-first order.** `contextual.Config.Fingerprint` (`internal/contextual/client.go:49`), `prerequisites` (`:254`), `modelReviewCell` (`internal/engine/matrix.go:134`), readiness `model_cli` capability (`internal/engine/readiness.go:205`). Caller of the `codex`-first order: the `clawpatch-review` lane (`internal/clawpatch/review.go:168`). The agent map is neither: `resolveMapProvider` (`provider.go:57-66`) is `codex`-only and stays so (design rev 2.5, Appendix 20).
3. **`CLAWPATCH_PROVIDER`.** Read by `resolveProvider` only when no provider is configured (`provider.go:36-38`); documented in `docs/references/environment-variables.md:37-39` as the review lane's provider when none is configured; named in design base lines 11 (historical Revision 2.5 paragraph), 109 (§4 Model CLI: "ignores the configured provider and `CLAWPATCH_PROVIDER`") and 350 (§10.2 workflow row: "constrain `CLAWPATCH_PROVIDER` to `codex`/`claude`"); in comments `internal/engine/config.go:16-17`, `internal/clawpatch/client.go:46`; set by tests `clawpatch/client_test.go:146,182,225-227,247,263-265,301`, `cmd/scout/model_cli_consent_test.go:29,47`. It is also **Clawpatch's own variable** (`.tools/clawpatch/734f81bc…/docs/providers.md:171,248,295,338`); Scout always passes `--provider <name>` (`modelInvocation`, `provider.go:68-73`), which takes precedence over it **[INFERENCE from Clawpatch's documented flag-over-env order; not run]**.
4. **When the orders can differ.** An opted-in lane needs an explicit provider: `parseModelCLI` rejects `model_cli.lanes` without `model_cli.provider` (`internal/policy/consent.go:134-146`), and `ApplyModelCLIPolicy` (`internal/engine/model_cli_policy.go:17-25`) copies that provider into both `Provider.CLI` and `ClawpatchProvider`. So a lane that actually runs always has an explicit provider and neither order is consulted; the orders differ only in what is reported or fingerprinted when no lane is opted in and both CLIs exist (`SCOUT_MODEL_CLI` is "honoured only when policy leaves the provider unset", which with lanes requires a provider means it affects reporting and the fingerprint, not a running lane) **[INFERENCE from `consent.go` and `model_cli_policy.go`; not run on a host with both CLIs]**.
5. **What is persisted.** `Config.Fingerprint()` (CLI name, model, prompt version) feeds `Plan.ModelDigest` (`internal/domain/types.go:648`, `internal/engine/assess.go:93`, `inventory/plan.go:179`), compared only in `matchingResumablePlan` (`assess.go:510`). No export or SQLite field stores a provider order or `CLAWPATCH_PROVIDER`.
6. **Design text.** The design states neither order (searched `first|order|auto-detect|tries` in base: no match for a provider order); `docs/references/environment-variables.md:30` says "With neither set, the first CLI found on `PATH` is used", `policy-file.md:28` "Takes precedence over `SCOUT_MODEL_CLI`". REQ-31 (line 54) lists `claude -p`, `codex exec` in that order.

### Decision 4 — CI install single owner

1. **Four copies of one install.** The composite action `.github/actions/scout/` (`action.yml` 113 lines; `install.sh` 56; `toolchain.sh` 28) and the two reusable workflows each download the binary and the Clawpatch bundle, verify sha256, and provision the pinned toolchain from the release tag: `scout-guardian-trusted.yml:83-121` (install) and `:122-147` (cache + provision); `scout-guardian.yml:66-104` and `:105-130`. About 59 duplicated lines per workflow and 84 in the action's two scripts.
2. **The action is unused by this repository.** `grep -rn "uses:.*actions/scout"` over `.github/`, docs and tests finds only prose: `uses:` in `scout-nightly.yml` are `./.github/workflows/scout-guardian.yml` (`:38`) and `scout-guardian-trusted.yml` (`:47`). The action first shipped in `aac3ca7`; every tag v0.1.0–v0.1.5 contains `action.yml` and `install.sh`, v0.1.2+ also `toolchain.sh` (`git ls-tree`). Its documented role (`docs/references/ci-integration.md:7,13,78`; `README.md:57`) is an adopter entry point; adopters are **unobserved**.
3. **It has drifted.** The action's "Run Scout" step (`action.yml:68-113`) runs `diff` or `assess` with no agent-map step, no `--fetch-pr-metadata`, no `fail-on-incomplete`, no evidence artifacts; the workflows do all four. The action detects four platforms (`install.sh:11-17`); the workflows hard-code `scout-linux-amd64` (`scout-guardian-trusted.yml:102`). Only the action is tested for install shape (`cmd/scout/guardian_workflow_test.go:206-253`, `TestCompositeActionInstallsFromVerifiedRelease`); the workflows' inline blocks have no equivalent assertion.
4. **Path semantics (GitHub documentation, fetched 2026-10-24, R-045).** "`./path/to/dir` … the `./` path resolves against the runner's workspace rather than the repository of the running workflow"; `$/` "references an action stored in the same repository as the workflow or action that is currently running, and resolves to that repository at the running commit … always resolves against the repository of the file it appears in, not the repository that called it … The `$/` syntax is not available in GitHub Enterprise Server"; `{owner}/{repo}@{ref}` is the cross-repository form (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax, "Using an action in the same repository as the workflow"). A reusable workflow **can** reach a local action: GitHub's contexts reference (`job` context example) checks out the workflow's own repository with `actions/checkout` `repository: ${{ job.workflow_repository }}`, `ref: ${{ job.workflow_sha }}`, after which `uses: ./<path>/…` resolves. The objections to that (option 4G) are that `actions/checkout`'s `path` is under `$GITHUB_WORKSPACE` (the assessed tree, the PR head on PR runs, from which §7.4 forbids running anything), that the action then runs at the workflow's commit rather than at `scout-version`, and that `job.workflow_*` is unavailable on GitHub Enterprise Server. `uses:` accepts no expression (GitHub contexts reference: `uses` is not a key that takes contexts; workflow syntax page above), so `owner/repo@ref` (4C) needs a literal owner and ref. GitHub Enterprise Server is not a supported host today: both workflows hard-code `https://github.com/${RELEASE_REPO}` for the download and the clone. Commit `2710447` has **landed** on `main`: both workflows default `RELEASE_REPO` to `${{ inputs.release-repo || job.workflow_repository }}`, the composite action to `github.action_repository || github.repository`, the dogfood caller passes only `scout-version: v0.1.5`, and `cmd/scout/guardian_workflow_test.go` rejects a hard-coded owner.
5. **Design text.** §7.4 (base line 203): "Reusable workflows split by trust level, plus a composite action: …"; "both reusable workflows and the composite action shallow-clone `release-repo` at `scout-version` outside the workspace, run that tag's `scripts/bootstrap-tools.sh` into `$RUNNER_TEMP`…"; REQ-25 (line 45) names the provisioning.
6. **The clone already exists.** Both workflows already shallow-clone the release tag with submodules (`scout-guardian-trusted.yml:141-146`, `toolchain.sh:24-25`) to run that tag's `scripts/bootstrap-tools.sh`; the scripts at the tag are the same trust as the binary (same tag, same repository).

### Decision 2 — Legacy baseline: required `uninspected` field instead of recompute

Options:

| Option | Behaviour | For | Against |
|---|---|---|---|
| 2A Keep recompute | absent field → banner + paired scan (status quo) | PR lane stays available across the upgrade | a tri-state (`nil` legacy / empty all / non-empty) travels through four layers (`ManifestMeta`, `Base`, `BaseState`, `resolveBase`); the only manifests that need it come from v0.1.0/v0.1.1 (published 2026-10-23) or from an earlier build's publish with no finalized run and no imported lane health, and none was observed (17 of 17 on `origin/scout/state` carry the field; other repositories unobserved) |
| **2B Required field (recommended)** | `LoadBase` refuses a manifest whose `uninspected` is absent or `null`; error text names the cause and remedy; `Gaps` is always non-nil | one meaning per value; the exporter always writes the field; a stale manifest cannot be silently trusted or silently recomputed around | PR runs between an upgrade and the first default-branch publish end `unavailable` (exit 3, neutral in `report`) for a repository whose branch tip was published by v0.1.0/v0.1.1, or by an earlier build from a store with no finalized run and no imported lane health |
| 2C Required at every reader | `ReadManifestMeta` (also used by `Import` and `MergeState`) refuses | strictest | `state restore` fails in the trusted job, so the branch can never be republished: needs a manual branch delete |

Recommendation: **2B**, strictness in `baseline.LoadBase` only. `state restore` and `state publish` keep working with an old manifest, so the next trusted default-branch run on a release ≥ v0.1.2 that publishes (exit 0 or 1) heals the branch without manual steps (Facts 5–6). No manifest-schema bump: `scout.state/v1` stays (the field is added by `480949a`, written by v0.1.2+ for a publish with a finalized run; its absence is "invalid for diff", not a new format). The exporter always writes the field. `state restore` of a manifest without `uninspected` records no comparison identifiers: `Store.Import` replaces `export_base` when the manifest carries `uninspected` and otherwise deletes any recorded `export_base` (`importRows` refuses a store that holds issues, so a store that imported a zero-issue manifest can take a second import of the same repository, and a value left from the first would otherwise be re-emitted beside the second's records), so the later `baseInfo` found=false path (`export.go:337-381`) returns empty revision and digests with `[]UninspectedFamily{}`; with a recorded `export_base` whose `uninspected` is non-null, `baseInfo` re-emits its identifiers and lane health as today; a recorded `export_base` whose `uninspected` is `null` (written by a pre-2.7 build from a manifest without the field) is treated as none. Without a finalized run or a recorded non-null `export_base`, `uninspected: []` sits beside empty identifiers, which `resolveBase` already recomputes by the tool-digest case, never beside identifiers that pass the digest and revision checks (that would be fabricated lane health); identifiers are written beside lane health only when both come from the same run or the same imported manifest. (Peer alternative, rejected: keep the imported value and let the exporter omit the field when it is nil; it keeps the nil/empty tri-state in the exporter, the shape this cutover removes.)

Recommendation: **4E**. The design change is the removal of "plus a composite action" in §7.4 (D6): that clause is what makes the action a design commitment rather than leftover. 4E adds an interface constraint that inline steps did not have: a workflow at revision N runs scripts from the `scout-version` tag, so a tag without them (v0.1.0–v0.1.5) fails the install step, and the scripts' outputs (`SCOUT_BIN`, `CLAWPATCH_BIN`, `SCOUT_TOOLS_DIR`, `GITHUB_PATH`) and inputs (`SCOUT_VERSION`, `RELEASE_REPO` and the toolchain directory the cache step names) are a contract between workflow and tag (design §7.4). The validation of the two inputs stays in the workflow (it guards the clone: a `scout-version` is used as `--branch`), so the scripts assume validated input and say so in their header. 4F is the fallback if the user wants the adopter entry kept; it needs one more design sentence and an action test, and is not drafted.

Consequence for existing users' persisted state: none (no persisted Scout state involved). Adopters: a caller of the reusable workflows is unaffected in inputs and permissions (`workflow_call` interface unchanged), but must move its workflow (a `uses:` ref or a copied file) and its `scout-version` together, both at or after the release that adds the scripts: an older `scout-version` with a new workflow ends the install step with exit 3 naming the minimum tag. A caller that uses `uses: <owner>/scout/.github/actions/scout@<ref>` keeps working at any existing tag; upgrading its `@ref` past the release that removes the action breaks it **[adopters unobserved]**. The dogfood caller (`scout-nightly.yml`) uses the reusable workflows only.

## Judgement calls for the council

1. **1B over 1C: keep the v1 re-anchor.** The user's text (§3.3, Phase 1, R1, REQ-10) mandates it, and a v1 store at `user_version` 3 is the one legacy shape that plausibly survives (S3 bundles). The user can settle whether any exists; if none, 1C deletes `issue_migration.go` (247 lines) with its three tests and edits those four places. Assumption A13 records this.
2. **Refuse 4–11 and 1–2.** Versions 4–11 were development-only (Fact 2); versions 1 and 2 are Scout v1 stores that its last build migrated to 3 (nothing shows they were development-only). Both rest on the git history and the tags, not on a survey of machines **[INFERENCE]**.
3. **`schemaVersion` stays 12** rather than renumbering to 1: renumbering would strand every released store.
4. **2B at `LoadBase` only** so `state restore`/`state publish` keep working and the branch heals itself; 2C would deadlock the trusted job.
5. **Exit 3 for a stale manifest on PR runs** until the next default-branch publish (neutral in `report`). The alternative, recompute (2A), keeps PRs flowing but keeps the tri-state.
6. **`claude` then `codex`** (3B over 3C): chosen because it leaves `Detect`, the matrix and `Plan.ModelDigest` unchanged, and because REQ-31 and §6 list `claude` first; the review lane's default is removed, not re-routed (no product caller); Clawpatch's own default order is irrelevant since Scout always passes `--provider`.
7. **`CLAWPATCH_PROVIDER` is ignored, not rejected**: it is Clawpatch's variable and Scout's flag already overrides it. The alternative, a hard error naming the removal, is stricter but breaks unrelated standalone use of `clawpatch` in the same environment.
8. **4E over 4F: the adopter-facing action is cut.** Adopters are unobserved; tags v0.1.0–v0.1.5 keep the action. Script names `scripts/install-release.sh` and `scripts/ci-toolchain.sh` are this draft's proposal; the council may rename them.
9. **Input validation stays in the workflow** (it guards `git clone --branch`), so the scripts assume validated input, rather than duplicating the two regexes in the scripts and the workflow.
10. **R17 and A13 are new content** (not requested): they record the cost and the unobserved assumptions of decisions 1 and 2 and add no mechanism; the council may cut them.
11. **A new-store DDL equal to the migrated shape is an acceptance test** (Phase 1, D8): the cut is safe only if the two paths produce the same tables, columns (name, type, not-null, default, primary key, in order), indexes (name, uniqueness, origin, partial, and indexed columns with sort order and collation) and foreign keys, and the same `sqlite_schema` objects by type and name (`PRAGMA table_info`, `index_list`, `index_xinfo`, `foreign_key_list`; stored `CREATE` text may differ), and the fixture must be a real v1 store built from the v1 DDL, not a rewound current store (round-1 issue 7).
12. **The `Store.Open` guarantee is stated as the council's text, not a stronger one** (round 2 issue 3): SQLite's read-only protocol may create `-wal`/`-shm` side files for a WAL-mode store, so the claim is "database file not written, no lock, `artifacts/` or journal-mode change, nothing migrated", not an unchanged directory; `immutable=1` was not adopted because it asserts that the file cannot change and makes SQLite skip locking and change detection, which does not hold for a store another Scout process may be writing (R-047; the driver was not run, **[INFERENCE]**).
