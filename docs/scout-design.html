Scout design

A discovery-only CI guardian for one repository.

Does

  • Runs on pull requests, default-branch pushes, nightly and locally.
  • Records evidence-backed issues and code-health measurements in a durable ledger.
  • Blocks a PR only for issues it introduced, in checks the repository activated.
  • Puts code quality first; security, performance and architecture follow.

Does not

  • Fix code or run an approval workflow.
  • Run the target's tests. It reads CI artifacts whose provenance matches.
  • Produce an inertia score for gating, severity or forecasts.
  • Claim that agents degrade an adopter's code.
Governed design (AGENTS.md design rules). Appendix A is the normative requirement set; the Overview explains it and Appendix B summarises decisions. Where they differ, Appendix A prevails.

1 · Run flow

One pipeline. The trigger picks the lanes. Only trusted default-branch runs (push, nightly or dispatch) write the baseline.
deterministic code Jev typed decision (advisory) reasoning LLM via claude -p / codex exec (opt-in) humans gate and trusted write

Triggers

  • Pull request: differential against the base; read-only, no secrets.
  • Push to default: publishes scout/state; runs the onboarding agent map until one completes.
  • Nightly: full run, trend rules, opt-in LLM lanes; runs the onboarding agent map until one completes.
  • Local: scout assess, scout diff --base <ref>.

State

  • The SQLite ledger is the source of truth.
  • scout/state is its published copy, written with compare-and-swap.
  • PR runs restore it and never write it.

3 · Gate decision

A PR goes red only when a finding passes all four checks. Everything else is reported.

Exit codes

  • 0 clean · 1 blocked (above)
  • 2 incomplete: a required lane did not finish
  • 3 unavailable: bad input, a refused operation, or a required tool missing

Colours

  • ● code decides · ● a human decided earlier
  • ● recorded, not enforced · ● enforced
Activation: every repository starts in report. A check can activate after at least 14 days and at least 5 PR runs with a comparable base, with zero unwarranted would-blocks and unknown attribution in at most 10% of all PR runs in the window (a run counts once if it is comparison: none or has a base-gap unknown finding). A maintainer activates it with a PR to policy.yaml.

What counts as a comparable base

A base is comparable when it was evaluated under identical tool, rule and policy digests: a published baseline that records lane health, or a paired merge-base rescan under head's digests.

With no comparable base at all, the whole run is unknown and nothing is classified as introduced. With a comparable base whose scanner did not inspect a finding's family, that finding is unknown instead of introduced; guardrails.* findings are exempt from this per-family rule. Either way, a tool upgrade or a policy change cannot look like a new defect.

Exit-code precedence is 3 > 2 > 1 > 0.

4 · What the ledger records

Three record types plus association labels. Only an issue can block a PR.
Issue IDs never use line numbers or feature IDs, so shifting code or remapping features cannot create a fake “new” issue.

How issue identity works

An ID (issue:<family>:<ulid>) is minted once. Each new finding is matched to an existing issue by its anchor set: the rename-followed path, qualified symbol, rule key, normalised mechanism and evidence fingerprint.

  • Rule, path, symbol and fingerprint all match → same issue.
  • Only the fingerprint changed → same issue, flagged evidence_drift; the disposition is kept.
  • No symbol, and exactly one candidate in the file → same issue.
  • Renamed path → retry the steps above on the old path.
  • Two or more candidates → both stay open with ambiguous_with; they are never merged.

Line numbers and feature IDs are kept out of identity, so a PR that shifts code or a mapper change cannot create fake introduced issues.
