# Implementation plan: merge-time area association (design rev 2.8)

Source of truth: `docs/scout-design.html` REQ-139–REQ-159, REQ-29, REQ-86–REQ-102, REQ-10, REQ-48 and REQ-51; ADR-006–ADR-008; council sign-off `docs/adrs/2026-10-31-jev-merge-association/round-8.md`. Where this plan and the design differ, the design wins.

Status: Phases 0–2 are done (`1d4e0cc`, `3e89f23`); the remaining phases are tracked in `docs/plans/2026-11-06-remaining-work.md`. This file stays the per-phase specification.

Goal: ship the provisional, opt-in (off by default) association flow: residual files of each default-branch merge → Jev → `codex` Terra fallback → association records or maintainer-accepted pending areas, with a refresh guard. Every phase ends in a runnable scenario (REQ-168) and leaves `main` releasable with the lane off.

## Phase 1 — State: schema 13, associations, pending areas

Files: `internal/state/store.go` (`schemaVersion` 12 → 13; v1 re-anchor path to 13), new `internal/state/associations.go`, `internal/state/areas.go`, `internal/areas/areas.go`, `internal/state/export.go`.

- `associations` table, one row per decided cluster per run plus one per inherited file, with every field the design lists (run id, decision time, `LastAgentRefreshAt` in force, merge commit, cluster key and files, Jev scores and outcome, escalation reason, CLI name/version, reported model/effort, prompt/inputs/catalogue digests, raw answer, retries, latency, outcome incl. the `unresolved (reason)` values and `inherited` rule, fallback-skipped flag and reason, `stale`, `thresholds provisional`).
- `Area`: `status` (`active` | `pending` | `superseded` | retired), provenance (cluster id, decision id), `accepted_by`, `accepted_at`; `Active()` false for pending/superseded.
- Export `state/v1/associations.jsonl` (deterministic order); manifest lists it `absent` when empty/missing; import of a pre-2.8 export yields no associations; stores at version 12 are refused per REQ-10 and REQ-46 with the re-baseline remedy unchanged.
- Tests: export/import/export byte round trip with associations and pending areas; pre-2.8 export imports; v12 store refused with the remedy message; v1 re-anchor reaches 13.
- Scenario: `scout state export` / `restore` on a seeded store reproduces identical bytes; an old export restores cleanly.

## Phase 2 — Residual files and clusters (deterministic, no model)

Files: new `internal/association/` (`residual.go`, `cluster.go`), a git reader for first-parent merges of a push and their per-merge changes (none exists today; `internal/inventory/diff.go` gives change kinds only), the heuristic-ownership predicate already passed to `areas.Reconcile`.

- Port `owned_classify` exactly as the design states it: deletions dropped; markdown and media excluded; owner = active area or association record to an active area; modified-and-owned not decided; modified, unowned, not heuristic-owned → coverage gap; renames inherit (owned) or stay pending (pending, unowned, not decided even if heuristic-owned); variant siblings inherit; rule (f) for heuristic-only files; empty-only clusters inert; inherited records written (no model call). Not ported: the cross-scope rename and translation rules (design: unmeasured differences).
- Orchestration: for a default-branch push, take the base..head range, list first-parent merges oldest first, and for each merge use that merge's own changes and its revision's file contents and ownership; apply the merge's association records, inherited records and pending-path changes before classifying the next merge. Clusters decided by earlier pushes are never re-decided.
- Clustering by normalised parent directory + variant stem; ≤ 10 decided clusters per merge, hash-sampled as measured; rest `unresolved (pr_cap)`.
- Parity test (strongest check of the port): replay recorded merges from `evaluation/x2d-postrun-tuning/` (fastapi rounds 1–10, axum rounds 1–5 inputs: changed files, ownership at round start) through the Go code. Cases untouched by the two excluded pilot rules (cross-scope rename, `docs/<lang>/` translation) must give cluster keys, members and residual decisions identical to the pilot's recorded units; cases those rules touched are partitioned, asserted against the Scout result the design specifies, and listed in the test as intentional differences. Ship the needed fixture slices under `testdata/`.
- Scenario: `scout assess` on a fixture repo with a scripted push of three merges (merge 1 adds a residual file that a stub decision assigns; merge 2 modifies it; merge 3 renames it) shows the file assigned once, the modification not decided, the rename inherited, and nothing from an earlier push re-decided; no model is called.

## Phase 3 — `association` lane (Jev)

Files: `internal/decisions` (register `merge.covered@v1`, `merge.which_area@v1` with the pilot's frozen question text and GUIDE criteria; state builder: paths, change kind, role, first 60 lines per member, PR metadata or `pr_metadata: absent`, diff summary, ≤ 5 sample files per active area; 20 % hash-selected second permutation), `internal/policy/mapping.go` (`mapping.association.*` keys, defaults, bounds), `internal/engine/lanes.go` (push-only optional `signal` lane, `requires: decision-egress`), `docs/references/policy-file.md`.

- Compose: assign iff `which_area` confidence ≥ `t_choice` (0.535) and covered score does not call `none` (P(true) ≤ 0.40); permutation disagreement or low confidence → `unresolved`; `jev_failure`, `jev_cap`; skip reasons (disabled, no key, no acknowledgement, egress not allowed, `catalogue size` < 2 or > 255).
- Staleness: a change to a threshold, the question text, the Jev pin, the fallback prompt digest or the fallback model marks prior records `stale` (label kept, shown `stale`, never re-decided automatically); a catalogue-only change does not. One test per trigger plus the catalogue-only non-trigger.
- Tests: fake HTTP Jev (existing `decisions_test.go` pattern); zero model calls on PR and fork runs and on every skip reason (disabled, no key, no acknowledgement, egress not allowed); optional-lane exit-code invariance; health `failed` only when every attempted call fails; **replay test**: feed the saved fastapi rounds 8–10 Jev scores (`evaluation/x2d-postrun-tuning/window`) through the Go composer and require the Jev-only outcomes per cluster to equal `compose_window.py`'s (P_assign 64/67, unresolved 10/92).
- Scenario: on the fixture repo with a stub Jev endpoint, an enabled push run writes association rows, lane health `ran (n)`, exit code unchanged; disabled → `skipped (disabled)` and 2.7 behaviour.

## Phase 4 — `association-fallback` lane (codex Terra)

Files: `internal/modelcli` (codex-only invocation for this lane: `codex exec -m gpt-6.1-terra -c model_reasoning_effort=high`, read-only, ephemeral, scrubbed env, no tools; parse CLI-reported model/effort), new `internal/association/fallback.go`, prompt embedded from `evaluation/x2d-postrun-tuning/terra_prompt_v1.txt` (digest checked), consent capture in `scout init`, `internal/engine/lanes.go` (`requires: model-cli`).

- Answers `existing` (area id) → association; `new` → pending area (≤ `max_pending_per_run`, then unowned and counted). One retry, then `terra_failure` for error, timeout, any command run, model/effort mismatch, unparsable, unknown id; `fallback_cap` beyond `max_per_run`; `skipped (no model CLI | no consent)`; never runs `claude`.
- Tests: fake `codex` binary on `PATH` (scripted answers, mismatch, command-run, timeout); the fallback receives only this run's `none`/`unresolved` clusters, never `jev_failure`, `jev_cap` or `pr_cap` clusters or earlier runs' clusters; **replay test**: recorded Terra answers for fastapi rounds 8–10 reproduce Jev+Terra outcomes (71/77, 0 unresolved, 13 pending on gold-none).
- Scenario: fixture push with the fake `codex` creates one pending area and one assignment; with `codex` absent the lane is `skipped (no model CLI)` and clusters are listed unowned.

## Phase 5 — Area lifecycle and maintainer actions

Files: `internal/areas/areas.go` (`Reconcile` ignores pending; never retires an area with an acceptance; after a completed map marks pending areas and association records `superseded` per the "files that exist at the mapped revision" test, heuristic ownership excluded), `cmd/scout` (`scout areas list --pending`, `scout areas accept <id>`, `scout areas merge <pending> <area>`), summary and JSON output (`internal/engine/gate.go` Summary, `cmd/scout/main.go` emit).

- Maintainer authorization reuses the `scout triage` pattern (`--actor`, `--reason`, `--authorize`; writable store only, so PR and fork runs, which are read-only, refuse; every action is in the audit trail). `accept` makes the pending area active with origin `association` and `accepted_by`/`accepted_at`. `merge` resolves the pending area and writes association records moving its files' labels to the target area, without adding them to the target's agent-map `FileSet`.
- Tests: Reconcile table tests for pending, accepted-then-matched, accepted-unmatched-heuristic (kept), supersede with deleted/renamed paths; authorized accept and merge (provenance, removal from the pending list, resulting ownership, export/restore), and unauthorized or read-only attempts rejected with no mutation.
- Scenario: accept a pending area, run a map refresh fixture, confirm it survives an unmatched map; summary lists pending areas with files.

## Phase 6 — Refresh guard

Files: new `internal/association/guard.go` (pure function over exported rows + `LastAgentRefreshAt`), summary and `scout readiness` output.

- Fallback rate and pending-new rate exactly as REQ-156–REQ-159 (window of `window_merges` merges with residual clusters in the current `LastAgentRefreshAt` generation; merge filter; `min_clusters`; `unmeasured` cases; per-reason inclusion); first exceeding window sets `catalogue-stale` until `LastAgentRefreshAt` changes; recommends manual `scout map --refresh`, never starts it.
- Tests: table tests incl. no `codex`, all calls failing, partial availability, healthy-no-escalation window (`unmeasured`), generation reset; restore round trip reproduces window and flag (REQ-51).
- Scenario: scripted 25-merge history trips the flag, outputs show `catalogue-stale`, a completed map clears it.

## Order, size and verification

Phases 1–2 are model-free and can land first; 3 and 4 depend on 1–2; 5 depends on 1; 6 depends on 1 and 3–4 rows; 7 last. Each phase: `go test ./...`, the repo's lint gate, the phase scenario run and recorded in `docs/STATUS.md`. Parity/replay tests in phases 2–4 tie the Go code to the measured runs, so the shipped behaviour is the one the evidence describes.
