## Verdict
**15 open issues (High 6, Medium 7, Low 2). Not signed off.** Fix, then run a new round with both peers. Only that round may sign, after Main computes SHA-256 for the complete final signed set and the council checks it.

**Is non-certifying collection a complete wiring ADR or a narrowing of ADR-012?** It is a legitimate, complete **wiring** ADR, not a narrowing, provided the R1-08 and R1-14 fixes land:
- ADR-012 already says unproven completeness is "unmeasured, not an implementation license to weaken the design" (plan §2, §5).
- ADR-015 keeps every invariant and the route exposes `Complete=false`, so it never weakens the readiness predicate.
- It must stop claiming it "selects the production wiring left open by ADR-012" without qualification (`ADR.md:10`). The certifying event source is still unselected, so REQ-22/27/78 shadow readiness stays unmeasured (exit 2) in production indefinitely.

## Decision memo

1. **Recommendation:** Adopt ADR-015 as a non-certifying collection/triage wiring ADR after applying fixes R1-01 to R1-15. The core of those fixes:
   - Triage authority = GitHub-issued run context read before any untrusted step, checked against the REST run and run-attempt records, with numeric actor IDs and the first terminal record per action ID final.
   - A `none` sentinel value for the verdict, and an exact input grammar.
   - Explicit external-caller breakage from `actions: read`.
   - `persist-credentials: false`.
   - Exact step ids, `if:` expressions and exit mapping.
   - A `start` operation for the collection marker.
   - v1 records no event population and a bounded reassessment.
   - The 2-hour attempt deadline only; no lag or event-deadline numbers.
   - P25 checked against a signed `wiring-contract.json`, with digests looked up at the adoption commit.
2. **Alternatives:**
   - (B) Narrow the ADR to triage only and defer collection. Smaller surface, but triage would have no persisted events to act on.
   - (C) Select durable capture now (webhook/App). Could certify, but needs a new service and secret, which ADR-012/015 exclude; it needs its own ADR.
   - (D) Use `run-name`/`display_title` to corroborate inputs through REST. A partial check at best (free-text reason, length); optional, not required.
   - (E) Check P25 digests against the current tree. Rejected: it breaks on the next edit to a living document.
   - (F) Keep the surface contract only in Go fixtures. Two sources of truth; rejected in favour of the signed contract file.
3. **Evidence:** the citations in the table, plus the plan §2 (dispatch and `actions: read` need a wiring ADR) and §6 (no invented durations).
4. **Risks:**
   - [INFERENCE] UI choice preselection.
   - REST `pull_requests` coverage for forks.
   - Scanner read-access proof depends on P23 running on real Linux and macOS.
   - Adoption-commit lookup needs full history (CI already has it).
   - Every external caller breaks once on upgrade.
   - All of these are reversible through a superseding ADR. The signed history is immutable.
5. **Execution outline:**
   1. Main revises ADR.md, adds `wiring-contract.json`, and updates the design REQ-25/160/161 rows, ci-integration (grants, minimum version, concurrency/re-run notes), cli-commands (reserved), STATUS, the plan, the README index and ledger rows R-102 onward.
   2. Write `round-1-response.md` mapping each issue to its fix.
   3. Hold round 2 with both peers. Main computes SHA-256 of every file in the final signed set (9 or 10 files); the council checks it against the `scout-signoff/v1` block; sign off only with zero issues.
   4. In the implementation PR: P25 adoption-commit gate and contract equality, updated guardrail tests, P23 credential-read fixture, then the provider capability/refusal and rollout receipts.
