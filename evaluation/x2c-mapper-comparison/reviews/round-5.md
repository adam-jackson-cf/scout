## The change verified

**What changed.** `validation/validate.py` l.45 reads `KEY = "sk-or-v1-" + "validation-stub-key-0123456789"  # a fake key, only ever given to the scorer subprocess and the stub`. Round 4 reviewed the same line as a single literal `"sk-or-v1-validation-stub-key-0123456789"`. Two adjacent string literals joined by `+` are folded by CPython at compile time; the characters read one by one give the round-4 value exactly. Reason for the change: the staged-tree Gitleaks gate (`docs/STATUS.md` l.211) reported a `generic-api-key` hit on that line; splitting is the repository's existing precedent for synthetic fixtures (`internal/analyzers/gitleaks_test.go` l.79 and `internal/issues/secret_e2e_test.go` l.26 both write `"AKIA" + "IOSFODNN7EXAMPLQ"`), not a written rule (N1).

**Nothing depends on the literal's source form.** Every use of `KEY` is the runtime value: `jev_env()` l.151–152 sets `OPENROUTER_API_KEY` for the scorer subprocess; `run_scorer` l.155–157 always passes `-endpoint stub.url`; the J key-hygiene check l.463–464 tests `KEY not in blob` (scores file + stdout + stderr + stub log); the alias refusal l.485 uses `jev_env()`; the missing-key run l.486 strips the variable; the C end-to-end run l.655 sets `OPENROUTER_API_KEY=KEY` with `X2C_JEV_ENDPOINT=stub.url`. The stub records only `auth_present` (a `Bearer ` prefix), `auth_len` and `body_has_key` (`"sk-" in json.dumps(body)`) (`validation/stub_jev.py` l.8–9, l.58, l.67–68); l.456 asserts the first and third, which hold for the unchanged runtime value. `validate.py` never reads its own text (`__file__` only at l.28 and in the fake-CLI bodies). No S planted-effect or planted-null check reads `KEY`; they reach the scorer through `pipeline()` → `run_scorer`, where only a non-empty key matters. The scorer itself reads the key from the environment and names only the variable in its error (`jev/main.go` l.300–303).
