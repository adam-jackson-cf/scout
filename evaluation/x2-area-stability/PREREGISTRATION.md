## 1. Question and hypothesis

Agent maps are unstable: between independent runs only 5–34 % of agent feature IDs recur (E3, R-031), and Clawpatch 0.7.3 agent IDs overlap 0.06–0.16 between
fresh runs (CP07 §5, R-032). Scout therefore keeps **areas**: `areas.Reconcile` matches each new agent feature to a prior area by file-set Jaccard at or above
`mapping.areas.match_jaccard` (default 0.5 **[ASSUMPTION, X2]**) and keeps the area's `scout_area_id`. Phase 4's scenario saw 53/56 (fastapi) and 40/47 (axum) area IDs
still active after one refresh at 0.5: design rev 2.3 (adopted 2026-10-23, `docs/scout-design.md` §11 Phase 4) calls this **area-ID retention** (an area matched *or kept*), not X2's matched-only survival below; X2 reports area-ID retention per transition as the cross-walk (§3.2). Phase 4 also saw 16 of 93 retained areas with file-set Jaccard < 0.8; whether the threshold is right, and whether a match joins the *same concern*, was left
to this study (`docs/STATUS.md` §1).

**Construct.** Under `Reconcile` an unmatched prior area is not lost: it stays active with its ID (`Kept`) or retires (`Retired`). "An area keeps its ID" is therefore not
the measured quantity. What is measured, and what HD5 and the decision rule below mean by **survival**, is *a prior area is matched by a next-map agent feature* (it takes that
feature's file set and title and keeps its ID through a refresh that re-maps it). Unmatched areas are reported as created / kept / retired (§3.2) and, over several refreshes, by the
chained fold (§3.6). Phase 4 also cited a per-area file-set Jaccard ≥ 0.8 **[ASSUMPTION, X2]** (design §11 Phase 4); this study reports the Jaccard distribution of matches (median, share < 0.8; §3.2)
but **does not decide it** (design rev 2.3 replaced that criterion with reported area-ID retention and Jaccard figures).

- **HD5** (`docs/hypothesis-ledger.md`): there is a Jaccard match threshold at which Scout areas are matched by a next feature (survive a refresh) for **≥ 80 % of prior areas** with **≤ 5 % spurious merges**
  (an area matched to a feature covering a different concern), in both reference repositories.
- Decision rule (design §13 X2, made precise in §4): adopt the threshold yielding both; else refresh the agent map only at onboarding and manually.

Out of scope: issue anchoring (areas never enter issue identity), inertia series keys (areas are labels; scopes derive from heuristic features and directory scopes),
mapper quality, Clawpatch versions other than 0.7.3, languages other than Python and Rust, and any change to `docs/scout-design.md` (needs its own council design round).

## 3. Measures

### 3.1 Replay unit
For a transition, the **prior areas** are `areas.Reconcile(nil, prev active agent features)`: one area per agent-mapper feature with ≥ 1 owned file in the prev map. The **next** map's
active features are reconciled against them with `areas.Reconcile(prior areas, next features, HeuristicOwner(next), {MatchJaccard: t})`. Every grid threshold uses the same code Scout runs
(`go run ./evaluation/x2-area-stability/replay`). Each transition is one step from the prev map's areas, so survival is per refresh and labels are threshold-independent (the multi-refresh behaviour is §3.6).

### 3.2 Survival
A prior area **survives** at threshold `t` iff `Reconcile` matches it (§1 construct). Per transition: `survival = matched / prior areas`.
**Primary estimand for a repo and stratum:** the mean of per-transition survival over its *measured* transitions (equal weight per refresh, computed and compared as an exact rational: C1 is `mean ≥ 4/5` in `fractions.Fraction`). The area-pooled proportion
(with its Wilson interval, treating areas as independent: anticonservative) is reported beside it, with the per-transition values (transition IDs retained) and the worst transition. **Weighting note:** survival weights refreshes equally while the spurious rate (§3.3) pools matches, so a map with more matches weighs more there.
Also reported: created, retired (fully heuristic-owned and unmatched) and kept areas, the **upper median** (`sorted[n // 2]`) Jaccard of matches and the share of matches with Jaccard < 0.8 (descriptive; Phase 4's per-area criterion is not decided here).
**Area-ID retention cross-walk.** Per transition and per stratum the analysis also reports `(matched + kept) / prior areas` (and its per-refresh mean; analysis fields `survival_kept_inclusive` and `survival_kept_inclusive_mean`), design rev 2.3's area-ID retention, the construct of Phase 4's 53/56 and 40/47. It is descriptive and enters no decision.

### 3.3 Spurious merge
A **match** (prior area ↔ next feature) at threshold `t` is **spurious** iff its label is `different_concern` (§6). Rate = spurious / labelled matches (labelled = `same_concern`, `overlapping_concern`,
`different_concern`), counted over match *occurrences*; labels are per unique `pair_id`, so one label can serve several occurrences and **unique labelled pairs are reported beside occurrences**. Sensitivities, reported not decisive: **strict** (spurious = `different_concern` + `overlapping_concern`) and **worst case** ((different + unlabelled) / all matches).
Matches without a usable label are `unmeasured` (§7), split into `cannot_tell`, unparsable and never labelled, never `same`. A repo/threshold with matches but no labelled match has an **undefined** spurious rate (§4).

### 3.4 Threshold grid
`t ∈ {0.30, 0.35, …, 0.90}` (13 points, exact `p/100`). The design default 0.5 is on the grid. Because `Reconcile` is greedy best-first one-to-one under a total order (Jaccard, area ID, feature ID), the matches at `t` are exactly the matches at
`T_MIN = 0.30` whose Jaccard is `≥ t`; `build_pairs.py` verifies this on every transition and aborts if it fails. **Only the matches at `T_MIN` need labels**, which is what lets one
labelling pass serve all thresholds.

### 3.5 Coverage diagnostics (descriptive, preregistered)
Per transition (in every replay row): prev and next agent feature counts, distinct owned files in each map and in both, and the number of prior areas with **zero** file overlap with every next agent feature (a survival ceiling no threshold can lift). They let a `fallback` be attributed to coverage swings or a degenerate exit-0 map
(Clawpatch fails only on zero valid seeds, `agent-mapper.ts:164-167`) rather than to the threshold. Not used in any decision.

### 3.6 Chained survival (label-free secondary measure; reported, not gating)
The replay folds F1→R1→R2→M1→M2 (T3–T6) through `Reconcile` with **accumulating** areas at every grid threshold (matched areas take the feature's files; unmatched areas persist as kept; created areas join), reporting per step: active prior areas, matched, created, kept, retired, and the share of the original F1 areas matched at every step so far.
Reported at `t*` (or at the design default 0.5 when nothing is adopted). It states the multi-refresh behaviour Scout's production reconciliation would show on these maps; it is not used in a verdict. If a chain map is unmeasured the later steps are unmeasured; a skipped M2 map is unmeasured, so T6 is unmeasured in the chain (the chain row exists with `status: unmeasured`).

### 3.7 Leave-one-transition-out view of `t*` (descriptive; not out-of-sample)
Per arm, **leave-one-transition-out by the adopted rule**: for each measured decisive transition `h`, `h` is held out **in every repository**, each threshold is classified **jointly** over the repositories on the remaining transitions (`pass` under C1–C3 in all repositories; the §4 gates are not re-applied), `t* = max(pass)` as in §4 (`none` when no threshold passes), and each repository's held-out survival of `h` at that `t*` is reported with its matched, labelled and `different` counts (`analysis.loto`). Selecting `t*` per repository from its own pass set (a superset of the joint set) would evaluate the held-out transition at a stricter threshold than the adopted rule, and is not used. `t*` sits at the survival edge by construction, so this is the cheapest view of how much of the margin is selection. It **understates** selection and is not an out-of-sample test: the held-out transition shares prior maps with the remaining ones (F1 in T1–T3; R1, R2, M1 in two each) and can share pair ids and labels (`build_pairs.py` deduplicates pairs by their blinded state), and holding out the only measured mutation transition selects `t*` from remap transitions alone (the §4 gates are not re-applied). It is not used in a verdict; the decision also reports `survival_margin_at_t_star` (the minimum over repositories of mean survival at `t*` minus 4/5).

## 4. Primary decision rule (per arm; arm A decides)

For each grid threshold `t`, using the `decisive` stratum (all six transitions) of **each** repository separately (no pooling across repositories):

- **C1** per-repo mean survival `≥ 4/5` (exact rational);
- **C2** per-repo spurious rate (point) `≤ 1/20` (exact; undefined when there is no labelled match);
- **C3** precision guard: Wilson 95 % upper bound of the per-repo spurious rate `≤ 0.10` **[ASSUMPTION: twice the design limit; a bound above it means the labelled matches cannot show compliance]**. What C3 establishes is stated in §7.

Every repository is evaluated before a status is assigned. `t` is `fail` iff C1 or C2 fails in any repo (a repo with no match fails C1); otherwise `imprecise` iff C3 fails in some repo **or the spurious rate is undefined (matches but none labelled) in some repo**; otherwise `pass`.

**Verdict**, applied in this order; the reason names the gate that tripped:
1. **Class gate.** `inconclusive` if a repo has fewer than 2 measured `remap` transitions or fewer than 1 measured `mutation` transition (this subsumes the former "< 2 measured production transitions" gate).
2. **Label gate.** `inconclusive` if the unlabelled share (`cannot_tell`, unparsable, never labelled) of decisive matches at `T_MIN` exceeds `1/10` in a repo. Control pairs (§5) are excluded from this share.
3. **Control gate (label validity), pooled across arms.** The labelling session, guide and controls are common to both arms, so the gate is computed once over all control pairs and applies to both arms (per-arm counts are reported descriptively; this is the one coupling between the arms). Per kind (content-swapped, identical-record), over the controls that carry a usable label (`same_concern`, `overlapping_concern`, `different_concern`; the §3.3 definition), a **miss** is any usable label other than the expected one (swapped: `same_concern` **or** `overlapping_concern`; identical: `different_concern` **or** `overlapping_concern`). `inconclusive` if, for either kind: misses exceed 20 % of the usable controls; **or** fewer than max(10, half of the generated controls of that kind) are usable (`cannot_tell`, unparsable and never-labelled controls are reported separately); **or** no control of that kind was generated although ⌈fraction × unique real pairs⌉ were wanted (generation shortfalls are reported; with no real pair nothing is wanted and the gate does not apply) (§5, §6).
   **Implied minimum sizes.** The gate needs at least 10 usable controls of each kind, and ⌈0.04 n⌉ identical and ⌈0.08 n⌉ swapped controls are generated from n unique real pairs. The identical kind therefore needs ⌈0.04 n⌉ ≥ 10, i.e. n ≥ 226 unique real pairs, and the swapped kind ⌈0.08 n⌉ ≥ 10, i.e. n ≥ 113, pooled across arms, for the gate to be satisfiable. The expected n is about 1 000 (§9); a heavily failed collection reaches `inconclusive` by this route (the reason names the usable-control minimum).
4. If the `pass` set is non-empty: **`adopt t*`**, `t* = max(pass)`. **Rationale:** a spurious merge mislabels persistently (the area then carries two concerns) while a missed match only mints a new area, so the strictest threshold that still keeps ≥ 80 % is chosen. `t*` sits at the survival edge by construction (a planted case adopts at survival exactly 0.80); RESULTS reports its margin.
   **Contiguity is not a verdict condition**: the spurious rate is a ratio of nested counts and oscillates by single matches near 5 %, so a non-contiguous `pass` set is an expected sampling outcome. It is reported as a flag and **must be stated in any design proposal that cites X2**.
5. Else if `imprecise` is non-empty → `inconclusive` (the data cannot show compliance).
6. Else → **`fallback`**: no threshold meets the criteria; the design's fallback applies (agent map only at onboarding and manually).

Consequence (not part of this study; a later council design round decides): `adopt t*` proposes `mapping.areas.match_jaccard` default `t*` (A1 resolved), `fallback` proposes removing refresh-on-merge, `inconclusive` leaves A1 as an assumption and needs a new preregistration. The design may cite X2 only if this document and scripts are signed off, the run followed them and the arm cited is probe-consistent (§2) (design rule 3).
The conclusion is a **one-step** (per-refresh) result on the clean state layout (§2); the chained survival (§3.6) is the multi-refresh picture and its direction relative to one-step survival is unknown.

**Arm B** is analysed with the same rule. **Replication status**, an ordered rule (the first clause that applies decides): (i) `not applicable` when arm A did not adopt `t*`; (ii) else `not citable (arm A probe-inconsistent)` when arm A is probe-inconsistent (§2); (iii) else `not citable (arm B probe-inconsistent)` when arm B's gates (class, label, control) pass, `t*` is `pass` in arm B and arm B is probe-inconsistent; (iv) else `replicated` iff arm A is probe-consistent, arm B's gates pass, `t*` is `pass` in arm B and arm B is probe-consistent, otherwise `not replicated` (reported with arm B's verdict and its own `t*`).
The control gate (gate 3) is pooled: arm B's control labels enter it, so a failed gate makes both arms `inconclusive`. Arm B's own survival, spurious rates, class and label gates never change arm A's verdict. **Consequence of arm B:** `adopt t*` proposes a *provider-general* default only if B is `replicated`; otherwise (`not replicated`, or `not citable (arm B …)`) the proposal is scoped to the codex provider and A1 stays an assumption for claude; if arm A is probe-inconsistent no consequence of this section applies. A design change citing X2 must state arm B's status.
**Ledger state (HD5, `docs/hypothesis-ledger.md`; fixed here, not left to the author after the data):** arm A `adopt` and probe-consistent → `supported` (scoped to the codex provider unless arm B is `replicated`); `fallback` and probe-consistent → `not-supported` **for the codex provider (arm A)** on this grid under `x2-concern-v1/guide-1` (not `refuted`: HD5 is existential and this grid, guide, two repositories and one run each are the only evidence); `inconclusive`, or arm A probe-inconsistent → `inconclusive`. Arm B never moves the HD5 state; the ledger outcome and `RESULTS.md` state arm B's verdict, its own `t*` and its citability beside arm A's. Citability is the §2 probe flag (served model identical across all probes of the arm, every probe taken without error, every `tool-versions` file present, no workspace-level configuration file present); a listed CLI-version change or a labeller-model change is reported beside the verdict and the ledger outcome, not folded into the flag. `results.json` carries `decision.citable` per arm and the replication status; `render` prints both.

## 5. Replay and pair construction
`run.sh replay` writes `transitions.json`, the replay JSONL (one row per arm, repo, transition, threshold: counts, coverage diagnostics and the list of matches), `chain.jsonl` (§3.6) and `replay-meta.json`. `run.sh pairs` (`build_pairs.py`) takes the matches at `T_MIN`,
verifies the prefix property, and writes `data/pairs/blinded.jsonl` (what labellers see), `key.jsonl` (the unblinded join, with which side is the earlier map) and `control-key.jsonl` (the sealed control key).
**Blinded state per pair:** for each side `title`, `summary`, `kind`, ≤ 8 entrypoints, ≤ 40 owned files (alphabetical truncation) and the total file count; for the pair the shared-file count and ≤ 20 shared files (alphabetical). Side order is fixed by a hash of the pair so position carries nothing.
`pair_id` is a hash of the whole blinded state in a side-order-independent form (entrypoints included), so identical evidence is labelled once and different evidence never shares a label.
**What is and is not hidden (validation check B):** no IDs, Jaccard or other score, threshold, transition, class, arm, provider or Scout decision is shown, and no only-left/only-right counts. The state does keep each side's owned-file total and the shared-file total (so that truncation is visible), from which the **Jaccard is exactly reconstructible**: shared / (left + right − shared). **Overlap is visible by design** (rules R2/R3 need the files), and file paths can identify the repository and carry the mutation markers (`x2_newpkg/`, `*_x2moved/`); labellers are not told, but the labels are therefore *not* blind to overlap (§10, threat "labellers see overlap"). Side order: the two sides are put in canonical order and a hash of the pair id decides which is on the left; `key.jsonl`'s `left_is_prev` is computed per occurrence from that order.

**Known-answer control pairs.** Mixed into `blinded.jsonl` with no marker, from a deterministic hash ranking of the real pairs: **content-swapped** controls (⌈8 %⌉ of the unique real pairs: a real matched pair with one side's title, summary and entrypoints replaced by those of an unrelated feature of the same map; files unchanged; expected `different_concern` by R3) and **identical-record** controls (⌈4 %⌉: both sides are the same record; expected `same_concern`).
Swapped controls are internally inconsistent records (the donor's entrypoints lie outside the side's files) and the identical-record control is an attention check, not a test of over-calling `different`: together they test inattention and gross anchoring at the source pair's overlap, **not** the 0.3–0.6 Jaccard regime where `t*` is chosen. Controls enter no rate; the control gate (§4.3) is their only decision use. They are reported with their label distribution (including `cannot_tell`), misses by kind, per-arm counts (descriptive), the swapped miss rate by the source pair's Jaccard band, generation shortfalls and A/B κ.
**Over-call check (descriptive).** The controls do not test the regime where `t*` is chosen, so one over-call check is preregistered at the other end: the share of `different_concern` among the labelled matches in the top Jaccard band `[0.90, 1.0]` (`over_call_check_band_90`, per arm and repository, as occurrences with its denominators: `different`, labelled, band matches), printed by `render`. A high share is consistent with a labeller that over-calls `different` or with a genuine different concern at a near-identical file set (`GUIDE.md` R3: the same files under different stated purposes); the two are not separable here. The share is reported beside the primary spurious rate and never changes the verdict.

## 6. Labels (agent protocol)

Labels come from the agent protocol of `AGENTS.md` ("Jev labelling", R-039), not from a human: a blind pass by two independent ephemeral sessions, `claude -p --tools ""` (default model) and `codex exec -s read-only` (read-only sandbox, empty working directory, no network, user config and rules ignored: the session setup of `evaluation/jev-triage-labels-v1`), each following the
frozen guide `GUIDE.md` (`x2-concern-v1/guide-1`), plus an adjudicating session (`claude -p --model sonnet`) where they disagree or one fails. The final label has provenance **`agent_reviewed`**, never `human`.
Labels are appended, never edited (`label.py` refuses a second run for the same guide version). A `--new-round` labels **only the pairs that have no usable final label** (final label `unparsable`, or a pair never labelled after an interrupted run), writes each pair's label rows and then its call row once the pair is complete (a kill in between leaves a labelled pair without a call row, which the analysis reports as `labelled_pairs_without_call_row`; never an orphan call row), and the analysis uses the first usable label per pair. A lock file `labels.lock` refuses a concurrent run; `read_jsonl` fails loudly, naming file and line, on a malformed line. **Recovery of a killed run:** confirm no run is active, delete `labels.lock`, truncate a partial trailing line, record the event under `Deviations`, then `--new-round`. `build_pairs.py` refuses when `labels.jsonl` has rows for the guide version, and the wrappers `run.sh pairs` and `run.sh replay` refuse on any row (labels are bound to the pair ids). Label sessions (A, B and the adjudicator) run with Scout's credential scrub (`common.scrub_env`), so no API key or base URL can switch them to API billing or re-route them (R-036). Session answers are copied field by field (`label`, `rule`, `reason`, `which`), never merged wholesale.
Label set: `same_concern`, `overlapping_concern`, `different_concern`, `cannot_tell` (definitions and rules in `GUIDE.md`). Sessions get one retry on unparsable output; a pair still unusable is `unmeasured`.
Reported: A/B raw agreement and Cohen's κ on **round-1 calls of real pairs** (controls separately; rows of a later `--new-round` are excluded from agreement), the adjudication rate and the **share** of adjudicated pairs, among those C answered validly, in which C's resolved model equals A's, with its denominator (C is `--model sonnet`, which may equal claude's default), the number of **codex sessions** (the sum of B's attempts over those pairs: one retry is allowed) and the number of **pairs** in which any codex attempt printed an `exec` event (`pairs_with_exec_event`; `exec_events` is summed over a pair's attempts, so a per-attempt split is not kept; real pairs of round 1 only, controls and later rounds are not counted; the read-only sandbox can read the disk, including the key files **[INFERENCE: sandbox semantics and transcript format]**; a count of 0 is uninterpretable until the transcript format of real output has been seen), the distinct **served models per session role** (A, B, C) with the number of call rows over every call row (so a model roll during the 3–4 h labelling run is visible; a call row keeps only its final attempt's model, so a model seen only on a failed first attempt is not recorded), the label distribution by arm, repository, class and by threshold band (the grid intervals `[t, t+0.05)` of the match Jaccard, the last `[0.90, 1.0]`), and the over-call check (§5).
**Labels are used only for HD5's spurious-merge rate.** They are not compared against any Jev output.
Caveat stated up front: no human checks these labels (user decision 2026-10-23), the labellers are the same model families that produce the maps, and the labels measure concern identity as the guide defines it. The controls test inattention and gross anchoring at the source pairs' overlap and gross label invalidity; they do **not** bound anchoring in the 0.3–0.6 regime where `t*` is chosen, nor concern judgement itself (§10).

## 7. Uncertainty, multiplicity, unmeasured

- **Intervals.** Wilson 95 % for every proportion (survival pooled, spurious). They treat areas and matches as independent, which they are not (areas within a map share structure and the same agent run);
  they are therefore reported as precision indications, and the decision rule uses a per-refresh mean for survival and requires both repositories separately. **Cluster by repo:** with two clusters a
  cluster-robust interval is uninformative, so none is computed and no cross-repository claim is made; generalisation beyond fastapi and axum is an `[INFERENCE]`.
- **Multiplicity.** The 13 thresholds are a selection set, not hypothesis tests: no p-values, no family-wise correction. The selection rule is deterministic (§4). The optimism of choosing `t*` on the same labels
  is not removed. C3 is a precision floor, not a bound on selection optimism; the arm B replication is stated and reported with it (never as a bound), and `RESULTS.md` states it.
- **`unmeasured`.** Counted and shown: transitions lost to failed, stopped or skipped maps (with reason), maps retried or failed (inventory), mutation skipped, areas with no prior areas, matches with no usable label (`cannot_tell`, unparsable, never labelled, reported separately). Unmeasured matches are excluded from the spurious denominator and bounded by the worst-case rate; more than 10 % of decisive matches at `T_MIN` makes the verdict `inconclusive` (§4 gate). The unlabelled share at `t*` and the worst-case rate at `t*` are reported prominently: one `AT t*` line under each arm's verdict, per repository (`at_t_star`).
- **What C3 establishes.** `adopt` means: a point spurious rate ≤ 5 % **and** a Wilson upper bound ≤ 10 % in both repositories, under the stated label protocol. It is *not* a demonstration that the true rate is ≤ 5 %: a 5 % upper bound would need ≤ 2 `different` in 150, an effective 1.3 % criterion, which would silently change the design's 5 % point criterion.
- **Precision at the expected size.** About 40–50 prior areas per map (E3/Phase 4: 33–49 agent features, 47–56 areas) gives roughly 6 × 45 = 270 decisive areas and ≤ 270 matches per repo. Wilson 95 %: survival 36/45 → [0.66, 0.89];
  spurious 0/150 → upper 0.025, 7/150 → 0.093, 8/150 → 0.102 (fails C3 although point 5.3 % also fails C2), 0/32 → upper 0.107 (too few matches to pass C3).
- **Operating characteristics** (exact binomial; both repos independent; adoption **at one threshold, conditional on C1 passing there, treating matches as independent: anticonservative** (no selection over the 13 nested thresholds, no cluster effects); `analysis.operating_characteristics`, asserted in validation). The labelled count at a passing threshold is about **216–270 occurrences per repo** (C1 needs ≥ 0.8 of ≈ 270 prior areas matched and every match is labelled; fewer unique pairs because F1 is shared), not 150: 216–270 is the expected size and 150 a stress case. P(adopt at one threshold, both repos) at a true spurious rate of 3 % / 4 % / 5 % / 7 % / 10 %:
  n = 150 (adoption needs ≤ 7 spurious per repo) 0.840 / 0.558 / 0.273 / 0.029 / 0.0002; n = 216 (≤ 10) 0.878 / 0.564 / 0.232 / 0.011 / < 0.0001; n = 270 (≤ 13) 0.931 / 0.646 / 0.267 / 0.009 / < 0.0001. C3 stops binding at n = 140 (7/140 = 5 % has Wilson upper 0.0996).
  At the expected size a mapper truly at 5 % spurious is therefore not adopted at a given passing threshold about three times in four, and one at 4 % about two times in five. Selection over the nested thresholds raises the chance of adopting at some threshold, and **selection inflation on real maps stays unmeasured**: S12's Jaccard spread has only two C1-feasible match sets ({0.30, 0.35} and {0.40, 0.45}) and 30 seeds, so it shows the ordering of P(adopt) and agreement with the table (it saw 0.30–0.33 at 5 %), not the size of the selection effect; the study says so before it runs. Validation S12 checks the pipeline end to end against this table with Jaccard-independent Bernoulli labels at 3, 5 and 7 %.
- **What the control tolerance implies for C2.** The control gate tolerates a 20 % miss rate on swapped controls. If the labeller's real sensitivity to a different concern were 80 % with no false positives, a true 6.25 % spurious rate would read as 5 % and pass C2. The controls bound inattention and gross anchoring, not that sensitivity; an `adopt` is compliance under this label protocol (§10), and the over-call check (§5) is the only descriptive look in the opposite direction, and it cannot separate over-calling from a genuine different concern at near-identical files.
- **Implied minimum sizes of the control gate.** Satisfiable only with ≥ 226 unique real pairs for the identical kind and ≥ 113 for the swapped kind (§4 gate 3); the expected ≈ 1 000 clears both, a heavily failed collection does not and reaches `inconclusive` by that route.

## 9. Budget and stop rule
Maps: 2 arms × 2 repos × 7 = 28 maps at 2–7 min each (E3: 119–297 s; Phase 4 onboarding: 424 s fastapi, 227 s axum), plus retries: about 2–3 h wall, subscription CLIs, no API keys; Clawpatch reports no tokens or cost (E3), so none is recorded.
Labels: unique pairs ≈ 6 transitions × ≈ 45 matches × 2 repos × 2 arms before deduplication (≈ 1 000 pairs) plus ≈ 12 % controls, two sessions each plus ≈ 25 % adjudications; ≈ 3–4 h at 4 workers.
**Stop rule (per `collect.py` invocation, i.e. per (arm, repo)):** before each map the invocation checks its own wall clock (limit **8 h**, started at invocation) and the count of consecutive failed maps (limit **3**); either condition stops that (arm, repo) before the next map, writes `data/stopped-<arm>-<repo>.json` with the reason, the next map and the maps not attempted, and is recorded under `Deviations`; maps not attempted are `unmeasured`. An abort (Ctrl-C, SIGTERM or SIGHUP to the collector, an exception; a SIGHUP that was already ignored when the collector started, as `nohup` sets it, stays ignored and aborts nothing) after the preflight and the before-probe, **including during the after-probe and the CLI-version collection that follows it**, ends the running process group the same way as a timeout and writes the same record with reason `aborted: <cause>` and a `phase` (`maps`; or `after-probe`, with all seven maps already recorded, `stopped_before: after-probe` and nothing left to attempt), sets any after-measurement not yet taken (`model_probe_after`, `cli_versions_after`) to `not taken: aborted` (one already taken is kept), and is recorded under `Deviations`. A session that can drop (SSH) runs the collector under `nohup … > log 2>&1 &` (its ignored SIGHUP is kept) or `tmux`; `setsid` only as `setsid … > log 2>&1 < /dev/null`, because the collector prints after each map and a write to a hung-up terminal fails with `EIO` [INFERENCE: tty hangup semantics], which would abort it (README); only a SIGHUP that reaches the collector unprotected writes the abort record, which refuses a rerun. A failure or abort during the setup between the before-probe and the first versions write (workspace creation, clone, checkout, version collection) writes no stop record and no data file; the rerun needs only the workspace removed (the message names it; a workspace directory left over, e.g. by a failed clone, is refused in the preflight before the before-probe). A skipped M2 runs no map and counts neither as a success nor as a failure. The four collections run in the order of §2.
**Per-call timeout: 1 800 s** for every Clawpatch call: `SIGTERM` to the process group (Clawpatch's own handler then kills its detached provider children, `exec.ts`), a 10 s grace, then `SIGKILL`; recorded as `rc` 124, `timed_out` and `ended_by`. Every `--version` call is bounded to 60 s. Inside a call, Clawpatch's provider timeouts are raised by Scout's `mapEnvironment` to 900 000 ms for **both** `CLAWPATCH_CODEX_TIMEOUT_MS` and `CLAWPATCH_CLAUDE_TIMEOUT_MS` (Clawpatch's defaults: codex 300 s, claude 180 s); the earlier statement here that "Clawpatch's own codex timeout (900 s) is unchanged" was wrong (§2). A timed-out attempt counts as a failed attempt.

## 10. Threats
- **Mapper variability is the thing measured.** Two repos, two providers, one run each of 7 maps; run-to-run variance of the agent is inside the estimates, not separable. Shared prior maps (F1 in three transitions; R1, R2, M1 in two each) make the effective number of refreshes smaller than six.
- **Pairwise decisions, chained report.** Production areas accumulate (a matched area takes the feature's file set; unmatched areas persist as `kept`). The verdict rests on one-step survival and labels; the chained fold (§3.6) is a label-free report of the multi-refresh behaviour. The direction of the difference is unknown.
- **M2 is a rename.** Path-based matching cannot follow moved files; its survival cost is whatever the replay measures (an area spanning moved and unmoved files can still match); it enters the decisive mean as designed and no effect size is pre-declared. M2 accumulates on M1.
- **Labels are model-made and unreviewed by a human.** Same model families as the mapper may share blind spots; κ between A and B is reported, adjudication is a third model session. Spurious-merge rates are bounded by label quality, and `RESULTS.md` says so.
- **Labellers see overlap.** The evidence necessarily shows file overlap (§5); a labeller could anchor on it, which would lower the measured spurious rate exactly where `t*` is chosen. The known-answer controls (§5) test for gross anchoring and inattention (content-swapped controls inherit the source pair's overlap, and a `same_concern` or `overlapping_concern` answer is a miss) and are bound to a pooled gate; they do **not** test the 0.3–0.6 Jaccard regime where `t*` is chosen, and do not prove concern judgement valid.
- **Concern identity is a judgement.** `GUIDE.md` fixes it; `overlapping_concern` is excluded from the primary spurious count and included in the strict sensitivity. If the strict rate fails C2 while the primary passes, `RESULTS.md` reports both and the verdict stays the preregistered one. Adoption is compliance under guide `x2-concern-v1/guide-1`, stated as such.
- **Replay boundary.** Scout's refresh reconciles `Map(agent)` output directly against the prior areas (`internal/engine/refresh.go:139-156`); the only follow-up heuristic map is the failure fallback (`internal/clawpatch/client.go:219-227`), and Clawpatch's `mergeMapResults` already includes the heuristic features. The replay therefore equals production for this step **up to tie order among equal-Jaccard candidates** (the replay mints area IDs with the snapshot strings `prev`/`next`, production with its own, and area IDs break exact-Jaccard ties, `areas.go`; the Python reference reproduces the replay's seed, so the R checks do not cover this), and `HeuristicOwner(next)` reads the same merged state. State-directory placement: X2 keeps the state outside the workspace; production's `<root>/.scout/clawpatch` is now excluded from Clawpatch's inventory (§2), so the layouts agree on what the agent sees.
- **Selection on the same labels** (§7). **Two clusters.** **Python and Rust only.** **Clawpatch 0.7.3 and default models only**; a different version or model needs a new study. **Truncation:** evidence shows ≤ 40 owned files and ≤ 20 shared files, alphabetically, with totals shown.
- **Agent maps may differ in repo coverage run to run** (E3: 435–742 owned files); survival is relative to the prior map's areas, so coverage swings appear as lost survival or created areas, both reported; the coverage diagnostics (§3.5) attribute them.
- **The served model is inferred.** Clawpatch reports only its option value; the model behind a map is taken to be the one named by the bracketing probes, which run in the maps' model-resolution context (§2: the providers' flags, Clawpatch's environment, the operator's own configuration, `CLAWPATCH_CLAUDE_BIN`; `CLAWPATCH_MODEL`, `CLAWPATCH_REASONING_EFFORT`, `CLAWPATCH_PROVIDER`, `CLAWPATCH_CONFIG` and `CLAWPATCH_CODEX_SANDBOX` are refused; workspace-level configuration is recorded by presence and makes the arm probe-inconsistent) **[INFERENCE]**. A roll that persists to the after-probe is detected, and a roll between the probes, a failed probe, a repository split or a workspace configuration file makes the arm probe-inconsistent (§2); a transient roll that the maps reached and that has reverted by the after-probe, and a weight change under the same model name, stay undetectable. §10's "a different version or model needs a new study" is checked against the probes, not asserted.
- **Arm–time confound.** The four collections run sequentially in the ABBA order of §2, so no arm is always later, but a model or load change over the collection window cannot be separated from arm or repository; the probes and the per-attempt `started_utc` make a roll visible, not removable.
