## 3. New issues

### Minor

**1. §4's replication-status rule is self-contradictory and its precedence lives only outside the frozen set.**
Location: `PREREGISTRATION.md:142`; `analysis.py:285-296`; `validate.py:353-356`; `reviews/round-5-response.md` judgement call 1; DRAFT-NOTES 29.
Evidence: `:142` reads "`replicated` iff arm A adopted `t*`, arm B's gates … pass, `t*` is `pass` in arm B and arm B is probe-consistent; otherwise … `not citable (arm A probe-inconsistent)` when arm A is, or `not applicable` when arm A did not adopt". The `iff` has no arm-A term, so the data "A adopts, A inconsistent, B passes and is consistent" satisfy `replicated` and `not citable (arm A …)` at once; "A inconsistent, B fails" fits `not replicated` and `not citable (arm A …)`; "A did not adopt, A inconsistent" fits `not applicable` and `not citable (arm A …)`. The code resolves these as not applicable → not citable (A) → not citable (B, only if would-be-replicated) → replicated/not replicated, but that order is stated only in the response and DRAFT-NOTES 29, neither frozen (§11 `:219`). §4 `:143` requires "a design change citing X2 must state arm B's status", so RESULTS prints a label the frozen text does not uniquely assign (rule 3: the preregistration fixes the decision rules). The unit case omits "A inconsistent, B fails" (`:354-356` has `rep(dB_ok, bad_a_)` but not `rep(dB_no, bad_a_)`), so moving the A check inside the `replicated` branch would return `not replicated` and still pass. The ledger state and proposal scope (`:143-144`) are unique in every combination; only the status label is not.
Required fix: rewrite `:142` as an ordered rule — (i) `not applicable` when arm A did not adopt; (ii) else `not citable (arm A probe-inconsistent)` when arm A is probe-inconsistent; (iii) else `not citable (arm B probe-inconsistent)` when arm B's gates pass, `t*` is `pass` in B and B is probe-inconsistent; (iv) else `replicated` iff B's gates pass and `t*` is `pass` in B, otherwise `not replicated` — with "arm A probe-consistent" inside the `replicated` definition. Add `rep(dB_no, bad_a_) == "not citable (arm A probe-inconsistent)"` to `validate.py:353-356`. No code change.

A wrong key or arm name at `:500` (e.g. `"consistent "`, or `.get("codex")` for both arms) would mark every real arm `NO`, make `replication` `not citable (arm A …)`, and under §4 `:144` turn a real `supported`/`not-supported` into `inconclusive` — a verdict-relevant failure that 222 passing checks would not detect (rule 4). Align §8 `:197` ("with arm B's probe flag set inconsistent" or, if the optional fixture is added, keep the wording).

**3. `fallback → not-supported` is unscoped although HD5 names no provider and arm B may have adopted citably.**
Location: `PREREGISTRATION.md:144`; `docs/hypothesis-ledger.md:29,33`.
Evidence: HD5 (`ledger:29`, §1 `:23-24`) asserts that *a* threshold exists, for Scout areas, in both repositories; no provider. §4 `:144` maps arm A `adopt`+consistent → `supported` "(scoped to the codex provider unless arm B is `replicated`)" but `fallback`+consistent → `not-supported` with no scope. Round 5 issue 1(c) asked that the mapping be "fixed here, not left to the author after the data"; this cell is the one where the author would have to improvise. `supported` is scoped; `not-supported` must be too.
Required fix: `:144` → "`fallback` and probe-consistent → `not-supported` **for the codex provider (arm A)** on this grid under `x2-concern-v1/guide-1` (not `refuted` …); arm B never moves the HD5 state, and the ledger outcome and RESULTS state arm B's verdict, its own `t*` and its citability beside arm A's".
