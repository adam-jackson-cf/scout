## 1. Question and hypothesis

Scout's agent map no longer uses "whatever codex or claude the operator has": `internal/clawpatch/client.go` runs `map --source agent --provider codex --model gpt-6-luna --reasoning-effort xhigh` (constants `mapModel`, `mapReasoningEffort`);
`resolveMapProvider` (`provider.go:57-66`) ignores the configured provider and `CLAWPATCH_PROVIDER` for mapping (they govern only `clawpatch-review`), always returns codex, and returns `modelcli.ErrNoCLI` (→ `skipped`) when `codex` is not on `PATH`; there is no claude path. Review and contextual lanes are unchanged. X2's verdict is for a different mapper (X2 never passed `--model`/`--reasoning-effort`; the codex arm's probes served `gpt-6.1-sol`).

- **HD5b**: for codex `gpt-6-luna` at `xhigh` invoked as Scout invokes it, there is a Jaccard match threshold at which Scout areas are matched by a next-map agent feature for **≥ 80 % of prior areas** with **≤ 5 % spurious merges** (X2 §1 construct, X2 §4 criteria C1–C3 and gates), in both fastapi and axum.
- Question for the design: which value should `mapping.areas.match_jaccard` take for the production mapper (§4a)?

Out of scope: issue anchoring, inertia keys, mapper quality, other models/efforts/providers (claude is not a mapper configuration any more), other Clawpatch versions or languages, any change to `docs/scout-design.md` (needs its own council design round).

## 4. Primary decision rule
X2 §4 unchanged for the codex arm: C1 per-repository mean survival ≥ 4/5 (exact), C2 per-repository spurious rate ≤ 1/20, C3 Wilson upper bound ≤ 0.10; verdict by the ordered class gate, label gate (≤ 1/10 unlabelled), control gate, then `adopt t* = max(pass)`, else `inconclusive` (imprecise), else `fallback`. A non-contiguous pass set, the survival margin and the unlabelled share at t\* are reported and **must be stated in any design proposal that cites X2b**.
**Citable** = X2's probe-consistency flag **and** the served/flags check (§2.4) **and** the replay contains no arm other than codex.
**What one arm costs.** (i) No replication: a design cannot claim the result holds for another model; that is acceptable because Scout's agent map is codex `gpt-6-luna` only (R-040), so the production configuration is exactly the one tested. (ii) No estimate of run-to-run variance beyond what one run of 7 maps per repository contains: the verdict is one draw of the agent per repository; X2 showed how near the edge a result can sit (margin 0.0035), and X2b adds no second draw to separate noise from effect. (iii) The control gate is no longer fed by a second arm: with one arm it needs ≥ 226 **unique** real pairs for the identical-control kind and ≥ 113 for the swapped kind (X2 §4 gate 3). **226 is necessary, not sufficient:** for 226–250 unique pairs exactly 10 identical controls are generated and `min_usable = 10`, so all 10 must be usable (one `cannot_tell` or unparsable control trips the gate). Pair ids hash the blinded evidence, so a mapper that reproduces records exactly across re-maps makes unique pairs fewer than labelled occurrences (X2 had equality). Validation shows the gate passing at X2's own per-arm planted size (480 unique real pairs), failing at 180, and at the exact boundary (225 fails with every control usable, 226 passes only if all 10 identical controls are usable). X2's codex arm had 436 unique labelled pairs at T_MIN (208 + 228); the smoke maps (26 / 76 agent features) suggest a similar or larger total **[INFERENCE from one map each]**, but see (iv). A collection that falls below the gate is `inconclusive` by it and is **not** repaired inside this study. (iv) **Expected labelled n per repository differs from X2's.** ≈ 0.8 × 6 transitions × the smoke agent-feature count **[INFERENCE]**: fastapi ≈ 125 (X2 fastapi had 45 prior areas at T1–T3; 41, 54, 32 at T4–T6), axum ≈ 365. X2's printed "216–270 labelled occurrences per repo" is X2's expectation, not X2b's; X2's `c3_stops_binding_at_n` = 140 is the first multiple of 20 at which an exactly-5 % count passes C3; at integer n a C2-passing count fails C3 only for n ≤ 126 (6 `different` needs n ≥ 120 for C2 and fails C3 up to 126), so with fastapi near 125 an `inconclusive` verdict through C3 (6 of 125: point 0.048, Wilson upper ≈ 0.101) is possible in that band and is stated here before any data. The analysis reports X2b's operating characteristics at n = 100, 125, 150, 216 and 270 and the expected n (`results.json` `x2b.operating_characteristics`, `x2b.expected_labelled_n_per_repo`); no decision rule changes.
**Cross-model confound.** X2b changes model and effort together (X2: model option `default`, probe-served `gpt-6.1-sol`, effort not recorded — `low` in the user's configuration **[INFERENCE]**; X2b: `gpt-6-luna`, `xhigh`); any difference from X2 cannot be attributed to either, and the comparison is descriptive only.

### 4a. Combination with X2 and the consequence for `mapping.areas.match_jaccard` (preregistered now; a later design round, under `AGENTS.md` design rules, decides)
**Reading of R-040.** R-040's "set the default from X2 and that repeat" is read as: **X2b decides; X2 enters as the reported cross-check** (in-pass-set flag, X2's t\* status in X2b, scope statement). A design round checks this reading against R-040. The alternatives were considered and rejected because each is worse on the stated grounds: *intersection* `max(P_b ∩ P_X2)` degenerates to "0.30 or nothing" because P_X2 = {0.30}, so a citable X2b `adopt` at 0.40 would leave 0.5 in place although X2b's own rule says 0.5 fails; *minimum* `min(t*_X2, t*_b)` can propose 0.30 when 0.30 fails C2/C3 in X2b and is the anti-conservative direction for spurious merges (X2 §4 treats merges as the costly error); *X2 as a tie-breaker on `inconclusive`* imports evidence from a model Scout does not ship exactly when the production evidence is uninformative.
X2b decides because it is the evidence about the mapper Scout ships; X2's codex result (frozen, digest-pinned in `x2b.X2_RESULTS_JSON_SHA256`; verdict `adopt`, t\* 0.30, pass set {0.30}, model `gpt-6.1-sol`) is a **reported cross-check on a different model** and never rescues, vetoes or shifts an X2b outcome. The preregistered proposal (`analysis_x2b.combine`, printed as `PROPOSAL`; always together with `x2b_t_star_in_x2_pass_set` and `x2_t_star_status_in_x2b`, X2b's own status at X2's 0.30):
- X2b `adopt t*_b`, citable → propose `mapping.areas.match_jaccard = t*_b` (a value is proposed **only** if it passes in X2b), always stated as "specific to `gpt-6-luna`/`xhigh`; in X2's pass set: yes/no" and, at 30, "grid minimum: nothing below 0.30 was measured".
- X2b `fallback`, citable → no threshold on the 0.30–0.90 grid meets C1–C3 for the production mapper (nothing below 0.30 was measured): the design's fallback applies (agent map at onboarding and manually; refresh-on-merge removed). X2's `adopt` at 0.30 is **not** applied to a model Scout no longer uses.
- X2b `inconclusive`, or not citable → `match_jaccard` stays 0.5 **[ASSUMPTION; X2 did not confirm 0.5, design A1]**; X2's 0.30 is **not** adopted in its place; a new preregistration is needed (a deviation that makes the run not citable is listed under `Deviations`).
- If X2's frozen result is unavailable (file absent or digest differs), `PROPOSAL` ends with "X2 cross-check UNAVAILABLE (<reason>)"; the proposal itself is unchanged.
The default stays 0.5 until a design round adopts a proposal; X2b's grid has only the 13 X2 points, so a proposal is always a grid value.

## 10. Threats
X2 §10 applies except the arm-B and ABBA items. Specific to X2b:
- **One run per repository, one arm.** The agent's run-to-run variance is inside the estimate; a result near the edge (margin) is fragile (§4).
- **Model and effort changed together**, and `gpt-6-luna` is a model name that may roll: the probes bracket each collection, but a probe echoes the flags it was given (§2.2), so a same-name server-side roll is invisible before *and* after; only a rejected or retired name is caught. `xhigh` may lengthen maps toward the 900 000 ms provider timeout on large inputs; a timed-out map is a failed attempt (X2 §9).
- **The served model is inferred** (X2 §10): the `agent-start` line reports the option passed, not the model served; the effort line of the probe is the banner's.
- **The probe banner format** (`model:` and `reasoning effort:` lines at line start on stdout/stderr of `codex exec`) was exercised once on 2026-10-23 (codex-cli 0.162.1; §2, "Pre-run measurement checks"): `model: gpt-6-luna`, `reasoning effort: xhigh`. The parser is the regex pair at `collect_x2b.py:310-313` (`^model:\s*(\S+)`, `^reasoning effort:\s*(\S+)`, multiline); a CLI that prints otherwise makes the before-probe refuse before cloning, with no data written.
- **Knowledge of X2** (disclosure above).
- **Code under test vs run tree.** Code under test is `2a2a346`; the run uses the run commit in a dedicated worktree (§2.6).
